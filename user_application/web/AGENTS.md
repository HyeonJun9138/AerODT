# AeroDT Web GUI 및 도메인 개발 규칙

이 파일은 `user_application/web` 아래의 공용 셸, GUI, UAM 및 Satellite 도메인 코드를 수정하는 개발자와 자동화 도구가 따라야 하는 규칙이다. 저장소 루트의 `AGENTS.md`를 먼저 적용하고, 충돌할 때는 루트의 계층·상태 소유권·검증 규칙을 우선한다.

## 1. 기본 원칙

1. 공용 셸과 도메인 기능을 구분한다. 지도, 창 배치, 공용 렌더링 품질은 셸의 책임이고, 운항 절차·임무계획·예측·도메인 음향은 해당 도메인의 책임이다.
2. GUI를 숨기는 것만으로 기능을 격리했다고 판단하지 않는다. 선택되지 않은 도메인은 폴링, 타이머, 오디오, 네트워크 쓰기와 무거운 계산도 시작하지 않아야 한다.
3. 브라우저는 현재 상태의 소유자가 아니다. 수신한 `StateSnapshot`을 화면용으로 투영할 수는 있지만 원본을 수정하거나 도메인별 현재 상태 저장소를 새로 만들지 않는다.
4. 미구현 기능을 다른 도메인의 화면에 연결해 구현된 것처럼 보이게 하지 않는다. `준비 중`과 미구현 범위를 명확히 표시한다.
5. 구조 이동과 동작 변경을 한 단계에서 섞지 않는다. 먼저 import와 시험을 보존하며 이동하고, 그 다음 활성화 조건이나 GUI 동작을 변경한다.
6. 기존 UAM 비행 기준선을 해치면서 도메인을 확장하지 않는다. 위성 도메인 추가가 UAM의 실행 순서, 제어, 물리나 서버 상태를 암묵적으로 변경해서는 안 된다.

## 2. 코드 배치

### 공용 셸에 둘 코드

다음 조건을 모두 만족할 때만 `user_application/web`의 공용 위치에 둔다.

- 둘 이상의 도메인이 같은 의미로 사용한다.
- 도메인별 운항 용어나 상태기계를 포함하지 않는다.
- 특정 도메인의 API, 폴링 주기, 음향 또는 임무 단계에 의존하지 않는다.
- 도메인을 선택하지 않은 상태에서도 안전하게 생성할 수 있다.

예: Cesium 뷰어 조립, 창 배치, 공용 지도 품질, 공용 버튼/폼 빌더, 도메인 선택기.

### 도메인 코드에 둘 코드

도메인 전용 코드는 아래에 둔다.

```text
user_application/web/domains/
  domain_catalog.js
  domain_chooser.js
  domain_shell.css
  uam/
    cockpit/
    operations/
    planning/
    live_twinning/
    prediction/
    analysis/
    audio/
  satellite/
```

UAM의 책임은 다음과 같이 나눈다.

| 폴더 | 포함할 책임 | 포함하지 않을 책임 |
|---|---|---|
| `cockpit` | PFD, NAV, 수동 조종, 조종석 카메라와 조작 표시 | PSU 배정, 서버 상태 소유 |
| `operations` | 조종사·운항사·버티포트·PSU 화면, 승인과 지상 절차 | 비행체 동역학, 일반 지도 구성 |
| `planning` | 항로, 수요, 단일·다중 비행 계획과 실행 화면 | 예측 모델 구현, 물리 적분 |
| `live_twinning` | 실시간 트윈 상태와 관측·동기화 표현 | 별도 현재 상태 저장소 |
| `prediction` | 예측 결과와 위험 표현, 모델 선택 UI | 학습 코드, 서버 추론 구현 |
| `analysis` | 운항 기록과 분석 조회·차트 | 현재 운항 상태 수정 |
| `audio` | UAM 기체와 현장 사운드의 브라우저 연결 | Satellite 공용 음향 가정 |

새 도메인을 추가할 때 빈 하위 폴더를 먼저 대량 생성하지 않는다. 실제 기능과 소유권이 생길 때 최소 폴더부터 추가한다.

### import 규칙

- 새 코드는 호환용 re-export 경로가 아니라 실제 `domains/<domain>/...` 구현 경로를 import한다.
- Satellite 코드에서 UAM 모듈을 직접 import하지 않는다. 공유가 필요하면 도메인 용어를 제거한 작은 공용 계약으로 추출한다.
- 공용 셸이 구체적인 도메인 내부 객체를 상태 저장소처럼 보관하지 않는다.
- 순환 import를 피한다. 도메인 구현은 공용 셸을 호출할 수 있지만 다른 도메인의 내부 구현을 호출하지 않는다.

## 3. 도메인 등록과 활성화

`domains/domain_catalog.js`를 도메인 표시 범위와 기능 가용성의 단일 출처로 사용한다.

새 도메인은 최소한 다음을 명시해야 한다.

- 안정적인 소문자 ID
- 사용자에게 보일 이름
- 표시 가능한 entity kind
- 사용할 수 있는 자료 source
- 음향 지원 여부
- 실제 구현된 화면과 준비 중인 화면

### 생명주기 규칙

도메인 모듈은 다음 순서를 따른다.

```text
모듈 import
-> 부작용 없는 생성
-> 사용자의 명시적 도메인 선택
-> activate(domain)
-> 필요한 조회·폴링·음향·도메인 카메라 시작
-> deactivate() 또는 pagehide
-> timer, listener, audio, pending request 정리
```

- import 시점과 constructor 안에서 네트워크 요청, `setInterval`, `AudioContext`, 시뮬레이션 실행을 시작하지 않는다.
- 시작은 도메인 선택 이후에만 한다. 종료 함수는 여러 번 호출해도 안전해야 한다.
- 선택 전에는 특정 도메인으로 자동 진입하지 않는다. 이전 선택을 저장해 다음 로딩에서 자동 실행하지 않는다.
- UAM은 기존 서울 진입을 사용하고 Satellite는 지구 전체 시야를 사용한다. 다른 도메인은 별도 카메라 정책을 명시해야 한다.
- 도메인 전환은 브라우저 화면의 전환이다. 공유 서버의 시뮬레이션을 `reset`, `stop` 또는 재시작하지 않는다.
- 조종 연결이 활성 상태라면 전환의 영향을 사용자에게 알리고 안전한 재진입 절차를 사용한다.

### 스냅샷과 설정 범위

- `scopeSnapshot`은 원본 entity와 snapshot을 수정하지 않는 얕은 화면 투영이어야 한다.
- 선택되지 않은 도메인의 entity, source와 알림을 화면 구성 요소에 전달하지 않는다.
- 도메인 선택 자체로 서버의 공유 수집 설정을 쓰지 않는다.
- `scopedLibraryApi`와 같은 범위 검증을 사용해 다른 도메인의 설정 쓰기를 거부한다.
- 공용 설정은 지형, 영상, 구름, 표시 품질처럼 의미가 정말 같은 경우에만 공유한다.
- UAM의 공역, 버티포트, 기체 사운드나 건물 운용 설정을 Satellite 설정에 노출하지 않는다.
- 같은 설정의 의미가 도메인마다 달라지면 별도 버전 키와 마이그레이션을 설계한다.

## 4. GUI 시각 규칙

### 공통 분위기

AeroDT 웹 GUI는 지도 위에 놓이는 저채도 청회색 항공·관제 인터페이스다. 새 패널이 독립 웹사이트처럼 보이거나, 도메인마다 전혀 다른 테마를 사용해서는 안 된다.

- 기본 배경: `#080e13`
- 기본 글자: `#e9f1f5`
- 보조 글자: `#c0d7df` 또는 `#a9c3d4`
- 공용 유리 패널: `var(--panel-glass)`
- 공용 테두리: `var(--glass-border)`
- 포커스: `#8edbea`
- 활성/선택 강조: `#9bdde8` 또는 기존 cyan 계열
- 정상/수신 중: `#a9e3c0`
- 경고: `#e5c394`
- 오류: `#f2b8a0`
- 비활성/대기: `#a9b8c0`

새 컴포넌트에서 위 색을 반복해서 직접 쓰지 않는다. 둘 이상의 컴포넌트가 사용할 의미 색이면 `styles.css`의 `:root`에 의미가 드러나는 CSS 변수로 먼저 올린다. 도메인 브랜드 색은 작은 배지, 선, 활성 상태에만 사용하고 패널 전체의 배경 체계를 바꾸지 않는다.

색만으로 상태를 전달하지 않는다. 텍스트, 아이콘, `data-status`, `aria-label` 중 하나 이상을 함께 제공한다.

### 유리 패널

지도 위의 일반 패널은 직접 배경을 다시 만들지 말고 `.glass`를 사용한다.

```css
.glass {
  background: var(--panel-glass);
  border: 1px solid var(--glass-border);
  border-radius: 12px;
  backdrop-filter: blur(var(--display-panel-blur, 14px)) saturate(.8);
}
```

텍스트가 흐려질 정도로 투명도를 낮추거나, 배경 blur를 컴포넌트별 애니메이션으로 바꾸지 않는다. 저사양 환경과 reduced motion에서도 읽을 수 있어야 한다.

### 모서리와 크기

| 요소 | 기준 |
|---|---|
| 상단 pill | 높이 `var(--top-bar)` 44px, 반경 `var(--top-bar-radius)` 22px |
| 일반 패널/카드 | 반경 12px |
| 드로어 외곽 | 열린 방향 16px |
| 일반 버튼·입력 | 반경 7px, 최소 높이 34px |
| 좌측 rail 버튼 | 반경 11px |
| 작은 카메라 도구 | 기존 9px 컨테이너 규칙 유지 |

새로운 반경 값을 임의로 만들기보다 위 계층 중 하나를 선택한다. 하나의 카드 안에서 서로 다른 반경을 과도하게 섞지 않는다.

### 간격과 배치

- 데스크톱 화면 가장자리 간격은 `var(--edge)` 22px를 사용한다.
- 700px 이하에서는 12px 기준으로 축소한다.
- 기본 간격은 4, 8, 12, 16, 22, 24px 계열을 사용한다.
- 좌측 작업 rail은 76px 기준이며 공용 셸의 소유다. 도메인 패널이 rail 위를 덮지 않는다.
- 상단 중앙은 시계, 좌측 상단은 표시 대상, 우측 상단은 도메인 변경처럼 공용 위치의 역할을 유지한다.
- 도메인 변경 버튼은 `.glass`, `--top-bar`, `--top-bar-radius`, `--edge`를 사용한다.
- 제거된 `운용 안내` 패널을 다른 이름으로 다시 만들지 않는다. 진단이 필요하면 설정 또는 명시적인 진단 모드에 넣는다.
- 카메라 화면과 지도를 가리는 고정 패널을 추가하기 전에 기존 작업 창 시스템을 사용한다.

### 타이포그래피와 숫자

- 글꼴은 `Inter`, `Segoe UI`, `Malgun Gothic`, sans-serif 순서를 유지한다.
- 본문은 11~13px, 패널 제목은 14~16px를 기본으로 한다.
- 영문 eyebrow는 9~10px, 자간 0.16~0.26em 범위로 제한한다.
- 한글에는 과도한 자간을 적용하지 않는다. 짧은 버튼과 제목은 `word-break: keep-all`을 우선한다.
- 고도, 속도, 시각, SOC처럼 비교하는 숫자는 `font-variant-numeric: tabular-nums`를 사용한다.
- 값과 단위를 분리해 읽히게 하며, 알 수 없는 값은 `0`으로 꾸미지 말고 `—`로 표시한다.

### 버튼과 상태

- 기본 버튼 스타일을 우선 사용하고, 특별한 목적 없이 새로운 색상 버튼을 만들지 않는다.
- 선택 상태는 `aria-pressed`, 펼침 상태는 `aria-expanded`, 탭은 적절한 tab role로 표현한다.
- 비활성 버튼은 이유를 `title`, 주변 설명 또는 상태 문구로 알린다.
- 위험 작업은 색상만 붉게 만들지 말고 동작 문구와 확인 절차를 제공한다.
- 로딩 버튼은 중복 요청을 막고, 성공과 실패 모두에서 다시 활성화되어야 한다.
- 전체 행을 클릭할 수 있다면 작은 내부 텍스트만 클릭 대상으로 만들지 않는다.

### 창과 메뉴 이름

- 작업 창 제목은 `UAM / Live Twinning`, `Satellite / Library`처럼 `도메인 / 기능` 순서를 사용한다.
- 기능 이름을 번역할 때 같은 개념에 여러 용어를 혼용하지 않는다.
- 서버 상태, 실제 구현, 추정값을 구분한다. `수신 중`, `저장 자료`, `준비 중`, `연결 실패`를 같은 상태처럼 표현하지 않는다.
- Satellite에서 UAM의 `운항 분석`, `Prediction`, `Stakeholders`를 재사용하지 않는다. 구현 전에는 해당 도메인의 준비 중 화면을 보여준다.

## 5. 반응형·접근성 규칙

- 1280×720과 1920×1080을 기본 검증 해상도로 삼고, 700px 및 540px breakpoint도 확인한다.
- 작은 화면에서 단순히 글자를 숨겨 의미가 사라지면 `aria-label` 또는 짧은 대체 문구를 제공한다.
- 키보드만으로 도메인 선택, rail, 창 닫기와 주요 설정에 접근할 수 있어야 한다.
- 포커스 테두리를 제거하지 않는다. 배경과 구분되는 2px 이상의 outline을 유지한다.
- dialog가 열려 있을 때 뒤쪽 지도 단축키가 실행되지 않게 한다.
- Escape의 우선순위는 현재 도구 취소, 선택 해제, 패널 닫기 순서처럼 명시적으로 관리한다.
- 아이콘 단독 버튼에는 `aria-label`과 `title`을 제공한다.
- 움직임은 `prefers-reduced-motion`을 존중한다. 상태 전달에 애니메이션 완료를 요구하지 않는다.

## 6. 성능과 자원 사용

- 렌더 루프에서 DOM 전체를 갱신하지 않는다. 값이 바뀐 경우만 쓰고, 보조 정보는 제한된 주기로 갱신한다.
- 패널이 닫혔거나 문서가 hidden이면 도메인 폴링과 시각 보조 갱신을 멈춘다.
- `setInterval`, event listener, Web Worker, AudioContext와 비동기 요청에는 대응하는 정리 경로가 있어야 한다.
- 스냅샷의 entity 배열을 복제해 장기 보관하지 않는다. 패널에 필요한 작은 합계와 최근 표시 이력만 제한해서 보관한다.
- 카메라나 도메인 전환 때 Cesium viewer, terrain 또는 동일 모델을 불필요하게 다시 만들지 않는다.
- 성능을 위해 정확도나 갱신률을 자동으로 낮추면 사용자에게 정책을 명시하고, 비행 계산과 화면 품질을 혼동하지 않게 한다.

## 7. API·오류·안전 규칙

- GET 실패를 빈 정상 데이터로 바꾸지 않는다. 마지막 정상값 유지, 오류, 미수신을 구분한다.
- UI가 임의로 승인, 허가, 배정, 임무 완료를 만들어내지 않는다.
- 서버가 소유하는 슬롯, Gate, FATO, 비행 단계와 현재 상태는 응답을 받은 뒤에만 표시를 확정한다.
- 사용자가 누른 요청은 pending ID나 sequence로 늦은 응답을 구분한다.
- 도메인 변경, 창 닫기와 화면 숨김은 서버 비행 종료 명령으로 해석하지 않는다.
- 공용 wire schema나 API를 변경하면 루트 규칙에 따라 ADR과 호환 시험을 추가한다.

## 8. 새 도메인 추가 절차

1. 도메인의 이해관계자, 현재 상태, 명령 소유자, 임무 단계와 데이터 출처를 문서화한다.
2. 공용 기능과 도메인 기능을 표로 나눈다.
3. `domain_catalog.js`에 표시 kind와 source 범위를 추가한다.
4. `domains/<id>`에 실제 첫 기능만 만든다. 미래 폴더는 만들지 않는다.
5. 선택 전에는 아무 도메인 부작용도 시작되지 않는 시험을 작성한다.
6. 다른 도메인의 entity와 설정 쓰기가 차단되는 시험을 작성한다.
7. 지구 또는 지역 진입 카메라 정책을 정한다.
8. rail과 작업 창 이름에 도메인 소속을 표시한다.
9. 미구현 메뉴는 숨기거나 준비 중으로 명확히 표시한다. 다른 도메인 기능으로 대체하지 않는다.
10. activate/deactivate 및 pagehide 정리를 검증한다.

## 9. 시험과 완료 기준

### 최소 자동 시험

- 변경한 모듈의 단위 시험
- 도메인 선택 전 무부작용 시험
- 선택한 도메인의 entity/source 범위 시험
- 다른 도메인 설정 쓰기 거부 시험
- activate/deactivate 정리 시험
- 주요 접근성 속성 및 GUI 구조 시험
- 전체 브라우저 시험과 변경 전 baseline 실패명 비교

브라우저 전체 시험은 다음을 사용한다.

```powershell
node --test project_support/tests/web_live/browser/*.test.mjs
```

기존 실패가 있으면 총 실패 수만 비교하지 말고 실패 이름을 정규화해 같은 baseline인지 확인한다. 관련 Python, C++ 또는 통합 경계를 변경했다면 가장 가까운 시험을 추가로 실행한다.

### 실제 화면 확인

- 사용자의 실행 중인 비행 탭을 임의로 새로고침하지 않는다.
- 별도 탭에서 시작 선택, 각 도메인의 카메라, rail, 설정, Live Twinning과 준비 중 화면을 확인한다.
- 1280×720에서 겹침, 잘림, 숫자 overflow, 배경 대비와 모서리 체계를 확인한다.
- UAM 확인 중 비행 시작, 허가 요청, reset 같은 운항 부작용을 만들지 않는다.
- 검증용 탭은 완료 후 닫는다.

### 완료 기록

의미 있는 작업을 마치면 루트 규칙에 따라 다음을 기록한다.

- 변경한 책임과 동작
- 실행한 시험 명령과 실제 결과
- 기존 baseline 실패와 새 실패 구분
- 실제 화면 확인 여부
- 서버 재시작 또는 사용자 탭 새로고침 여부
- 남은 위험과 미검증 범위

## 10. 코드 리뷰 체크리스트

아래 질문에 하나라도 답하지 못하면 완료로 표시하지 않는다.

- 이 코드는 공용인가, 특정 도메인 소유인가?
- 선택되지 않은 도메인에서도 요청, 타이머, 오디오가 시작되는가?
- 현재 상태를 브라우저에 중복 저장하거나 원본 snapshot을 수정하는가?
- 다른 도메인의 기능이나 설정이 노출되는가?
- 색상, 반경, 간격이 기존 토큰과 계층을 따르는가?
- 상태를 색만으로 표현하는가?
- 작은 화면과 키보드 접근이 가능한가?
- 닫기와 pagehide에서 모든 자원을 정리하는가?
- 미구현 기능을 정직하게 표시하는가?
- 전체 시험의 실패가 기존 baseline과 동일한가?
- 실제 화면에서 겹침과 잘림을 확인했는가?
