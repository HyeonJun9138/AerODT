# AeroDT Web Live Twin

전체 화면 지구와 Live Twin 상태를 표시한다. 항공기와 위성은 기본적으로 함께 표시되며, 화면 거리와 픽셀 크기에 따라 점과 대표 3D 모델을 전환한다. 현재 제품 시각화의 기준 구현은 이 CesiumJS 웹 앱이다.

## 실행

최상위 `python main.py`는 같은 포트를 사용하는 **같은 저장소 폴더의 AeroDT 런처**를
확인하여 종료하고 새 서버를 시작한다. Windows에서는 로컬 종료 이벤트로 정상 종료를
먼저 요청하고 최대 10초 기다린다. 이전 버전이라 이벤트를 지원하지 않거나 응답하지
않으면 확인된 서버 PID만 강제 종료한다. 따라서 재시작 시 실행 중인 작업은 중단될 수
있다. 다른 프로그램, 다른 저장소의 서버, 소유자를 확인할 수 없는 포트는 종료하지 않는다.

- 평소와 같은 실행: `python main.py`
- 기존 서버를 그대로 열기: `python main.py --reuse`
- 다른 포트: `python main.py --port 8767`
- 모듈 직접 실행 시 재시작: `python -m user_application.apps.web_dashboard.launcher --restart`

프로세스 식별에 `psutil`을 사용하므로 환경을 새로 만들 때 아래 requirements를 설치한다.
브라우저를 닫는 것만으로 서버가 종료되지는 않는다. 재시작 후 비행 변경을 보려면
브라우저를 새로고침하고 **새 비행 실행**을 생성한다. 과거 저장 실행은 변경하지 않는다.

환경이 준비된 현재 작업 폴더에서는 최상위 `python main.py`만 실행하면 된다. 저장 위성 + 로컬 인증 항공기/건물을 사용하고 CelesTrak는 중지한다. 아래 모듈 실행은 세부 옵션을 직접 선택하는 고급 실행이다.

저장소 루트의 PowerShell에서 실행한다. Python 3.10 이상이 필요하다.

```powershell
python -m venv project_support/environment/web_venv
& project_support/environment/web_venv/Scripts/python.exe -m pip install -r user_application/apps/web_dashboard/requirements.txt
& user_application/apps/web_dashboard/start.ps1
```

서버가 응답할 주소와 포트는 `user_application/configs/web_dashboard/default.json`의 `host`, `port`가 정한다. 런처는 그 값을 그대로 쓰고 시작할 때 열 주소를 출력한다. `--host`를 주면 그 실행에서만 덮어쓴다(`--host 0.0.0.0`이면 루프백을 포함한 모든 인터페이스). 루프백이 아닌 주소는 이 PC 밖에서도 접속되며 이 서버에는 로그인이 없으므로, 그런 주소로 실행하면 매번 경고를 출력한다. 현재 설정은 `0.0.0.0`(모든 인터페이스)이라 이 PC의 `http://127.0.0.1:8766`과 네트워크 주소 `http://103.218.162.73:8766`이 모두 열린다. 단일 주소(예: `103.218.162.73`)로 지정하면 그 주소만 응답하고 루프백은 거부된다. 단일 worker로 실행한다.

기본 구성은 user_application/configs/web_dashboard/default.json이다. CelesTrak GP(JSON) 수집을 시도한다. GP는 궤도 요소이며 화면 위치는 SGP4 계산 결과다. 공급자 연결 실패는 화면 하단에 표시되고 지구는 계속 사용할 수 있다.

항공기는 OpenSky 이용 허가를 확인한 뒤 opensky_enabled를 true로 설정하고 로컬 환경변수 AERODT_OPENSKY_CLIENT_ID와 AERODT_OPENSKY_CLIENT_SECRET을 지정해야 한다. 비밀값을 저장소, 화면 또는 채팅에 붙여 넣지 않는다. 항공기 보관과 요청 빈도는 계약/할당량에 맞춰 설정한다. 현재는 원본 항공기 응답을 디스크에 저장하지 않는다.

## 명시적인 화면 검증 모드

로컬 OpenSky 인증 파일을 준비했다면 `start.ps1 -OpenSky` 또는 다음 명령으로 실제 항공기 수집을 켠다.

```powershell
& project_support/environment/web_venv/Scripts/python.exe -m user_application.apps.web_dashboard --opensky
```

인증정보는 완전한 환경변수 쌍이 있으면 우선 사용하며, 없으면 `%LOCALAPPDATA%/AeroDT/credentials/opensky.json`의 `clientId`, `clientSecret`을 읽는다. 파일을 저장소에 복사하지 않는다. 일반 실행은 이 파일을 자동으로 읽거나 항공기 수집을 켜지 않는다. `--opensky`는 실제 공급자에 요청하므로 이용 권한과 할당량을 확인해야 한다.

```powershell
& project_support/environment/web_venv/Scripts/python.exe -m user_application.apps.web_dashboard --fixture-aircraft --fixture-satellites
```

시험 모드에는 가상 항공기 3개와 가상 위성 24개가 동일한 Data → Live 경로로 들어간다. FIXTURE / NOT LIVE가 표시된다. 실제 데이터 연동의 완료 증거가 아니다. 성능 시험은 추가로 --fixture-satellite-count 16000을 사용한다(상한 20000).

## 조작

외부 위성 요청 없이 저장 GP를 표시하면서 항공기만 수집하려면:

```powershell
& project_support/environment/web_venv/Scripts/python.exe -m user_application.apps.web_dashboard --opensky --saved-satellites data/workspace/live_ingestion/imports/sdc_active_20260907.json.gz
```

저장 GP는 Data에서 원래 수집 시각을 유지해 읽고 `cached` 출처로 Live Twin에 전달한다. 이 옵션은 CelesTrak 네트워크 수집을 끈다. 위성의 움직임은 저장 궤도의 SGP4 계산이며 실시간 수신이 아니다. 예시 파일은 로컬 생성물로 저장소에 포함하지 않는다.

화면은 지도 위에 얹은 얇은 유리 표면 하나로 통일한다. 왼쪽 끝에는 작업 영역 세로 rail이 있고 위부터 Live Twinning(현재 화면), Simulation(준비 중), 맨 아래 설정이다. 왼쪽 위에는 둥근 막대 안에 항공기·위성·UAM 버튼과 개수가 있다. 오른쪽에는 카메라 조작만 남기고 지도 표시 토글(태양 조명, 3D 건물, 지형 기복, 지역명)은 설정 패널로 옮겼다. 같은 버튼을 옮긴 것이므로 상태는 한 곳에서만 관리된다.

지도는 ArcGIS 직접 연결이며, 건물은 Cesium ion의 OSM Buildings를 사용한다. 제작 표기와 지도·엔진 출처는 검은 띠 없이 오른쪽 아래 모서리에 작게 겹쳐 표시한다. Cesium ion 로고와 공급자 출처는 이용 조건에 따라 계속 표시하며, 로고 폭 52 px과 9 px 글자로 최소화하고 긴 문구만 줄임표로 접는다. 전체 출처는 Data attribution 링크에서 그대로 볼 수 있다. 완전히 제거하지는 않는다.

- 드래그: 지구 이동과 회전. Ctrl+드래그: 시점 기울이기.
- 휠, +/−, 슬라이더: 부드러운 확대/축소.
- N: 북쪽 정렬. 내려다보기: 수직 시점. Home: 전 지구 초기화.
- 기체/위성 클릭: 상태 정보를 열고 그 대상까지 접근한 뒤 대상을 회전 중심으로 삼는다. 접근 거리는 모델 크기의 8배(300~3,000 m)이며 크기를 모르면 항공기 600 m, 위성 1,500 m다. 시선 방향은 현재 시점을 유지하고 거리만 바뀐다.
- 대상을 중심으로 둔 상태에서 드래그는 그 대상 주위를 공전하고, Ctrl+드래그는 대상을 중심으로 기울인다. 휠 확대는 모델 크기 바로 바깥에서 멈춘다. N/수직 시점도 대상 중심으로 다시 맞춘다. 대상이 움직이면 카메라가 따라가며 화면 중앙에 유지한다.
- Esc, 닫기, 빈 공간 클릭 또는 추적 끄기: 대상 고정을 해제한다. 카메라는 그 자리에 남고 회전 중심은 지구로 돌아온다. 대상 보기는 다시 접근해 중심으로 삼고, Home은 서울 기본 시야로 돌아간다.
- 지형이 카메라보다 높아지면 대상 고정을 유지한 채 대상 좌표계 안에서 카메라만 올린다.
### 외부 요청 보호 (수집 일정)

공급자는 프로세스가 아니라 **주소**를 본다. 재시작, 두 번째 대시보드, 검증 실행, 같은 PC의 다른
프로그램이 모두 한 명의 클라이언트다. 그래서 언제 다시 물어도 되는지를 프로세스가 아니라 파일이
기억한다: `data/workspace/collection/guard.json`(수집 일정, 저장소에 포함되지 않음).

- 요청 **전에** 슬롯을 잡는다. 요청 도중 죽어도 그 주기 동안은 다른 프로세스가 못 묻는다.
- 실패하면 **자기 주기보다 빨리 묻지 않고** 연속 실패마다 두 배로 늘린다(상한 30분~6시간).
- 301·302·400·401·403·404·410·451처럼 **다시 물어도 달라지지 않을 답**이면 자동 재시도를
  아예 멈춘다. 이 정지는 **재시작해도 유지**되며, Library에서 그 자료의 수집을 **껐다 켜야**
  풀린다(운용자가 확인했다는 뜻).
- CelesTrak에는 `If-Modified-Since`를 보낸다. 바뀐 게 없으면 304로 끝나 1.3 MB 대신 수백 바이트다.
  리다이렉트는 따라가지 않는다(따라가면 요청이 두 배가 되고 성공처럼 보인다).
- 언제 몇 번 물었는지는 같은 파일의 `journal`(최근 200건)에 남는다.
- 시험 입력(fixture)은 밖으로 나가지 않으므로 일정에 기록하지 않는다.

- 항공기와 위성은 모두 화면을 따라간다. 항공기는 공급자에 요청하는 범위가 화면을 따라가고,
  위성은 궤도 자료 전체를 그대로 둔 채 **화면에서 보이는 하늘에 뜬 것만** 매 초 계산해 보낸다
  (지평선 위에 있는지로 판단하므로 저궤도는 화면 부근, 정지궤도는 훨씬 넓게 잡힌다). 나머지
  궤도는 20초에 한 바퀴씩 나눠 훑어 새로 떠오르는 것을 찾는다. 지구 전체를 보고 있으면 실제로
  전부 하늘에 있으므로 전량을 계산한다. 두 가지 모두 Library의 '지도 화면 따라가기'로 끌 수 있고,
  끄면 위성은 전 궤도(16,507개)를 매 초 계산한다.
- 왼쪽 위 항공기·위성 버튼으로 각 레이어를 독립적으로 표시하거나 숨긴다. 기본은 둘 다 표시하며 서버 수집과 상태는 숨겨도 유지된다. UAM 버튼은 자리만 마련한 것으로, 연동 자료가 없어 누르면 준비 중임을 알린다.
- rail의 Live Twinning과 Simulation을 누르면 rail 옆으로 330 px 작업 패널이 열린다. 지금은 내용이 비어 있고 제목과 안내 문구만 있다. 같은 버튼을 다시 누르거나 × 또는 Esc로 닫는다. 한 번에 하나만 열리며 열린 동안 칩·상세 패널·설정 패널·시계가 그만큼 오른쪽으로 밀린다.
- Simulation은 아직 화면이 없다. 패널 안에 준비 중임을 표시하고 Live Twinning이 현재 화면으로 남는다. rail과 칩, 작업 패널, 설정 패널은 지도 로딩과 무관하게 동작한다.
- 기본 점은 두 종류 모두 3px, 선택만 6px이다. 항공기 주황색/위성 하늘색은 상태 노후화와 무관하게 고정하며 오래된 상태는 상세 정보에 표시한다. 3D 모델이 보이면 점은 숨긴다.
- 숨긴 레이어는 표시 좌표 갱신과 LOD 계산을 건너뛰고 모델/라벨을 해제한다. 렌더링 collection만 분리하며 현재 상태를 별도로 복제하지 않는다.

영상은 Cesium 및 영상 공급자의 외부 연결이 필요하다. 영상 실패 시 기본 지구와 경고를 표시한다. Cesium/WebGL 자체 실패는 재시도 화면이며 가짜 성공으로 처리하지 않는다. 임시 모델의 원본과 이용 조건은 digital_twin/model_library/visual_assets에 있다.

## 선택 대상의 궤적과 3D 모델 배정

- 위성을 선택하면 지구 위에 그 위성의 궤도를 함께 그린다. 저장된 궤도 요소를 SGP4로 전파한 한 궤도(최대 6시간, 최대 600점)이며 계산 결과이지 측정된 궤적이 아니다. 현재 위치 주변 ±240초는 2초 간격으로 촘촘히 표본화해 근접 확대에서도 위성이 선 위에 놓이고, 먼 구간은 넓은 간격을 유지한다.
- 항공기에는 경로를 그리지 않는다. 공급자 상태에는 저장된 항로가 없고 등속 외삽은 항로가 아니기 때문이다. 브라우저는 항공기에 대해 경로를 요청하지도 않는다. 실제 항로 표시는 별도의 track/flight 자료와 추가 요청이 필요하다.
- 경로는 Live Twin이 계산하고 `GET /api/live/trajectory/{entity_id}`가 읽기 전용으로 제공한다. 브라우저는 받은 점을 그릴 뿐 궤도를 전파하지 않는다. 갱신은 180초 간격이며 선택을 해제하면 멈춘다.
- 상세 패널은 궤도 주기·원지점·근지점·경사각·궤도 기준 시각 경과와 표시 구간을 보여 준다.
- 위성 3D 모델은 `digital_twin/model_library/visual_models/satellite_matching.json`의 규칙으로 배정한다. NORAD 번호와 이름의 정확 일치, 동일 계열, 계열군 순으로 판정하고 실패하면 정거장·큐브샛·궤도권(LEO/MEO/GEO/HEO) 대표 형상을 쓴다. 로켓 본체와 파편은 모델 없이 점으로만 표시한다. 상세 패널이 "해당 대상의 대표 모델 / 동일 계열 모델 / 대표 형상 / 모델 없음"을 구분해 표시하며, 이는 표시용 배정이지 실제 기체 식별이 아니다.
- 권리 검토가 끝나지 않은 자산은 배정하지 않는다. 현재 Starlink형·통신 버스형·GNSS 버스형·3U 큐브샛·GOES-R 모델 5개가 여기에 해당해 해당 계열은 궤도권 대표 형상으로 표시된다. `rights.public_export`가 정리되면 규칙 변경 없이 그 모델이 사용된다.
- 항공기는 공급자 상태에 기종 정보가 없어 대표 A320 형상을 유지한다.
- 지도·엔진 출처는 하단 footer에 한 번만 표시한다. 3D 미리보기 창은 로컬 모델만 그리므로 같은 로고를 창 안에 반복하지 않는다.

## Simulation: 버티포트 자산

- rail의 Simulation 패널은 항공기·위성·UAM 분류를 갖고, 버티포트 도구는 UAM 아래 버티포트/항로 탭에 있다. 이름, 위치(지도에서 선택: 모델이 커서를 따라오다 클릭한 곳에 놓이고 Esc로 취소 · 또는 지도 중심 좌표 · 또는 직접 입력), 배치 형태, 방향, 설계 기체(소형 D 8 m · 중형 D 12 m · 대형 D 16 m · 직접 입력), 판 높이, 게이트 수, FATO 수와 각 FATO의 이착륙 속성(FATO가 하나면 이착륙 고정)을 입력하면 서버가 배치를 생성해 지도에 미리 보여 주고, 저장하면 목록에 남는다. 방향은 입력 즉시 회전하고 다른 설계값은 서버 응답(보통 0.1~0.5초) 뒤 바뀐다.
- 치수는 설계 기체 D값(외접원 지름)에서 자동 산출된다: FATO 1.5 D, TLOF 0.83 D, 안전구역 0.25 D 또는 3 m, 게이트 1.2 D, 유도로 폭은 착륙장치 폭의 2배(미입력 시 0.35 D). 폼 아래에 산출된 FATO·게이트 지름, 유도로 폭, 판 크기가 표시된다. 인증 설계값이 아니다.
- 배치 형태: 가로 일렬(게이트 열과 FATO 열이 유도로를 사이에 둠), 세로 일렬(남북 유도로에 게이트를 세로로, 끝에 FATO), 양옆 이중(유도로 양옆에 게이트를 번갈아), FATO 중앙(FATO 좌우에 게이트). 모두 FATO 1개부터 된다. `digital_twin/model_library/vertiport_layout.py`가 원·판·지상 경로 망(노드·간선·길이)을 만든다.
- "지도에서 선택" 중에는 모델이 커서를 따라온다. 판 아래 지형 전체를 재서 가장 높은 지면 위에 놓으므로 묻히지 않고, 이동은 변환 행렬만 바꾸므로 매 이동 2 ms 안쪽이다. 같은 설계의 배치를 이미 갖고 있으면 첫 이동에서 바로 보인다.
- 지도에는 지형 위로 돌출된 사각 판(3D)과 그 위에 공항식으로 도장한 데크가 그려진다: 콘크리트 판 이음선, 아스팔트 유도 차선과 노란 중심선, 게이트의 노란 정지 원과 번호, FATO의 흰 파선 외곽선·TLOF 실선·중앙 `F`·역할 표기, 그리고 판 가장자리 빈 띠에 적힌 버티포트 이름. 판 기준(최고 지면 기본 · 평균 · 최저 · 직접 입력 고도)으로 높이를 조절하고, 폼 아래에 잰 지면 범위와 상면 고도가 표시된다. 350 m 밖에서는 이름 billboard, 8 km 밖에서는 점 마커로 보인다. 상단 UAM 칩이 저장된 버티포트 수를 세고 표시를 켜고 끈다.
- 버티포트 탭이 열려 있으면 지도의 버티포트에 마우스를 올릴 때 판 외곽선과 마커가 밝아지고 커서가 바뀐다. 좌클릭하면 그 자리에 카드(이름·요약·편집·보기·삭제)가 열리고, **우클릭하면 배치 때 쓰던 높이·방향·배치 도구가 커서 옆에 바로 열린다**(카드의 편집도 같은 도구를 연다). 도구에서 값을 바꾸면 지도에 즉시 보이고 저장을 눌러야 남으며, 취소나 Esc로 닫는다. "지도에서 위치 조정"을 누르면 다시 커서를 따라가고, 클릭한 자리에서 도구가 다시 열려 저장할 수 있다. 배치 중일 때의 우클릭은 예전처럼 배치 도구다.
- 탭은 폼이 위, 저장된 목록이 아래다. "생성된 버티포트 N"을 누르면 목록이 열린다.
- 정의만 `data/workspace/simulation/vertiports.json`에 저장되고 배치는 읽을 때마다 생성된다(옛 정의는 기본값으로 보완). API는 `GET/POST /api/simulation/vertiports`, `GET …/options`, `POST …/preview`, `GET/PUT/DELETE …/{id}`이며 검증 실패는 422로 필드명을 돌려준다. 목록의 "보기"는 그 위치로 이동하고, 삭제는 두 번 눌러 확인한다.

## Simulation: 항로 (지점·구간)

- UAM 분류의 **항로** 탭에서 만든다(옆의 **비행 계획** 탭은 다음 단계 자리). 패널에는 목록이 없다: 모드 띠(보기 / 지점 추가 / 구간 연결 대기 / 구간 연결), "＋ 지점 추가" 토글, 선택 해제, 개수 요약뿐이고 모든 관리는 지도 위에서 한다. "＋ 지점 추가"를 켜고 지도를 클릭하면 그 자리에 지점(점 마커)이 생기고 카드가 열린다: 이름은 비우면 주변 지명(OpenStreetMap, 동·리 수준, 겹치면 " 2", " 3")으로 채워지고, 고도는 1,000 ft 기본(ft/m 전환), 지면 기준(AGL)/절대 고도 중 하나이며 카드가 지면 고도와 절대 고도를 작게 함께 보여 준다. Esc는 카드 → 추가 모드 → 선택 순으로 닫는다.
- 지점·구간에 마우스를 올리면 밝아지고 커서가 바뀐다. 지점을 클릭하면 노란 점과 지면까지의 점선으로 선택되고 정보·수정·삭제·보기 카드가 열린다; 같은 지점을 다시 클릭하면 풀린다. 지점을 고른 채 다른 지점을 클릭하면 구간 카드(주황 태그): 종류(비행 프로파일 C Transition + Climb · D Departure Terminal Procedures · E Accel + Climb · F Cruise · G Decel + Descend · H Arrival Terminal Procedures · I Transition + Descend; 프로파일상 다음 구간을 강조)를 고르면 저장되어 그려지고, **순항(F)만** 회랑 폭(기본 300 m)을 물은 뒤 확인한다. 도착 지점이 선택되어 이어서 그릴 수 있다. 구간을 클릭하면 이름·종류(·F면 폭)를 고친다. 카드 헤더의 태그(지점 추가·지점·지점 수정 / 구간 연결·구간 수정)가 지금 어느 단계인지 말해 준다.
- 버티포트의 FATO는 지점이다: 이륙 FATO에서는 구간이 출발만(B → C), 착륙 FATO로는 도착만(I → J), 이착륙 FATO는 카드에서 어느 쪽으로 쓸지 고른다. FATO끼리는 바로 잇지 않는다. 지도에는 판 상면에서 hover 30 m까지의 원기둥과 작은 구로 서 있다.
- 순항 회랑은 외곽선 없는 반투명 면이고 지점마다 둥근 허브(그 지점에 닿는 가장 넓은 회랑의 반폭)에 맞춰 잘리며, 같은 지점에서 갈라지는 두 회랑의 겹침은 이등분선으로 나눠 한 번만 칠해진다. 나머지 구간은 같은 고도 곡선을 따르는 선이다. 고도는 양 끝에서 평평하게 시작·도착하는 곡선으로 이어진다. 상단 UAM 칩이 버티포트와 함께 항로 표시를 켜고 끈다. 항로는 그 지역을 볼 때만 그려진다: 카메라가 45 km보다 멀면 아무것도 보이지 않고, 지점 이름은 25 km, 구간 이름은 18 km 안에서 나온다.
- 지명은 지점 추가 모드에서 커서가 움직이는 동안 미리 받아 둔다(약 500 m 격자, 1초에 한 번). 서버도 같은 격자로 캐시하고 연결을 유지하므로, 처음 보는 자리는 0.4~1초, 근처는 즉시 채워진다.
- 저장은 `data/workspace/simulation/routes.json`(지점·구간만; FATO 끝점은 버티포트에서 읽을 때마다 유도). API는 `GET /api/simulation/routes`, `GET …/options`, `GET …/place?latitude&longitude`, `POST/PUT/DELETE …/nodes[/{id}]`, `POST/PUT/DELETE …/links[/{id}]`. 지명 조회는 `place_names_enabled: false`로 끌 수 있다. 자세한 결정은 ADR 0018.

### FATO 규칙과 건물 충돌 검사

- **FATO는 구간을 정한다.** FATO에서 출발하는 구간은 상승(C·D·E), FATO로 들어오는 구간은 강하(G·H·I)뿐이다. 이륙 FATO는 출발점으로만, 착륙 FATO는 도착점으로만 쓰이고, 이착륙 FATO는 카드에서 용도를 고르면 그에 따라 상승·강하가 정해진다. 프로파일 그림에서 다른 구간은 잠겨 보이고 눌러도 반응하지 않으며, 서버도 같은 규칙으로 거절한다(`segment` 필드).
- **이미 저장된 구간이 버티포트 수정으로 규칙과 어긋나면** 지도에 주황 점선으로 그려지고 요약에 `FATO 불일치 N`이 붙는다. 구간 카드가 이유를 말해 주며, 구간 종류가 문제면 저장 한 번으로 고쳐지고 방향이 문제면 FATO 속성을 바꾸거나 구간을 지운다.
- **건물 충돌 검사**: 항로 탭의 `건물 충돌 검사` 버튼이 모든 구간을 브이월드 건축물 도형·높이와 대조한다. 회랑(F)은 폭 전체를, 상승·강하 선은 좌우 25 m를 검사하고, 경로 높이는 지도와 같은 완만한 높이 곡선, 건물 바닥은 지도 지형(Cesium World Terrain)을 구간을 따라 100 m마다 잰 값이다. 건물 지붕이 경로보다 높으면 **충돌**(빨강), 30 m 안쪽이면 **근접**(노랑)으로 구간 색이 바뀌고 가장 가까운 건물 위에 이름·높이·여유가 표시된다. 새로 그리거나 고친 구간, 지점을 옮긴 뒤 닿는 구간은 저절로 다시 검사된다.
- 검사는 서버가 브이월드 건물 셀(0.01°)로 계산하므로 브이월드 키가 있어야 하고(`vworld.json`), 화면에 어떤 건물 자료를 띄웠든 같은 자료로 검사한다. 처음 검사할 때는 셀을 받아오느라 구간 8개마다 몇 초씩 걸리고, 같은 지역은 6시간 동안 서버가 기억한다. 검사 결과는 화면에만 있고 저장되지 않는다.

## Stakeholders: 이해관계자별 화면 (자리만)

레일의 `Stakeholders` 버튼이 이해관계자 섹션을 연다. 위에 Simulation과 같은 분야 선택(항공기 · 위성 · UAM)이 있고, UAM에서는 조종사 · 운항사 · 버티포트 · PSU 탭이 있다. 지금은 각 탭이 무엇을 보여 줄지 한 줄로 적힌 자리이며 실제 화면은 하나씩 채워 넣는다. 항공기·위성 분야는 준비 중이라고만 말한다. 섹션을 열면 Simulation 탭이 지도에 잡고 있던 것(배치 도구, 항로 카드)은 놓는다.

## Live Twinning: 상태 추정 (자료 정합)과 예상 경로

Live Twinning 패널의 **AI 모델 · 추정과 예측** 그룹에 두 장의 카드가 있다. `자산 상태` 그룹은 추적 중인 대상(항공기 · 위성 · UAM)만 담는다. 항공기 관측은 25~30초에 한 번 도착하므로, 그 사이를 무엇으로 메우는지가 화면 위 기체의 움직임을 결정한다. 카드 머리글에 지금 무엇이 돌고 있는지 나온다(예: `등속 외삽 적용 중 · 예상 경로 15초`).

| 카드 | 항목 | 뜻 |
| --- | --- | --- |
| 상태 추정 | 상태 추정 | 끄면 각 기체를 마지막 관측 자리에 그대로 둔다. 갱신마다 건너뛰고, 상태 산출은 `관측값`이 된다. 켜면 모델이 관측 사이를 메우고 새 관측을 3초 시상수로 흡수한다. |
| | 추정 모델 | 여기서 고른 모델은 **트윈의 상태 자체**를 만든다. 지도의 모든 것이 이 결과 위에 선다. |
| 항공기 예측정보 생성 | 예측정보 표시 | 켜면 항공기를 클릭했을 때 모델이 보는 앞길이 그려진다. |
| | 예측 모델 | 기본은 **추정 모델과 동일**이라 화면의 기체와 그려진 경로가 같은 가정을 따른다. 일부러 다른 모델을 고를 수 있다. |
| | 예상 구간 | 몇 초 앞까지 그릴지. 기본 15초, 5~120초. |
| UAM 예측정보 생성 | 예측정보 표시 | 켜면 UAM을 클릭했을 때 앞길이 그려진다. |
| | 예측 모델 | 외삽은 지금 쓸 수 있고, 전달받은 UAM 전용 학습 모델은 임무 경로까지 넣어야 한다. |
| | 예상 구간 | 기본 60초, 10~240초. 학습 모델의 시간 범위(10 · 90 · 240초)에 맞춘 범위다. |

**두 카드를 나눈 이유**는 둘이 다른 일이기 때문이다. 추정은 매 tick 추적 중인 전부에 적용되어 트윈의 상태가 되고, 예상 경로는 고른 하나에 대해 화면에만 그려진다. 무엇보다 **한 모델이 둘 다 할 수 있는 것은 아니다** — 학습된 GRU는 예측만 하고 관측을 융합하지 못하므로 추정 모델로는 아예 제시되지 않는다. 자세한 내용은 ADR 0034 2차.

### 예측은 항공기와 UAM이 다른 일이다

같은 "앞길 그리기"지만 입력이 근본적으로 다르다. 항공기는 밖에서 관측되므로 우리가 가진
것은 위치 이력뿐이다. UAM은 우리가 날리므로 남은 임무 경로를 트윈이 들고 있다. 그래서
두 자리로 나뉘어 있고, 각 자리에는 거기에 쓸 수 있는 모델만 나온다.

| | 항공기 예측정보 생성 | UAM 예측정보 생성 |
| --- | --- | --- |
| 외삽 (등속 · 선회 보정) | 사용 가능 | 사용 가능 |
| GRU 직접예측 v1.1 | 사용 가능 | 목록에 없음 (항공기 궤적으로 학습) |
| UAM 단기 · 중기 · 장기 | 목록에 없음 | 사용 불가 (아래) |
| 추정 모델과 동일 | 사용 가능 | 없음 |

### 전달받은 UAM 학습 모델 세 벌

`UAM_Prediction`의 short(10초) · mid(90초) · long(240초). 저장소에는 넣지 않는다. 한 벌이
57 MB이고 전달 형태가 PyTorch pickle이라 대시보드가 도는 곳에서 열 물건이 아니다.

```bash
<anaconda python> project_support/tools/import_uam_prediction_models.py "임시폴더/UAM_Prediction"
```

한 번 돌리면 `data/workspace/prediction/uam_route_mlp/`에 safetensors와 manifest로 들어가고,
이후로는 torch도 pickle도 필요 없다. 자료가 없으면 세 모델은 목록에 남되 어떻게 넣는지를
말한다.

**지금은 돌지 않는다.** 가중치는 왔지만 각 부분이 어떤 순서로 이어지는지가 오지 않았다.
출력단이 받는 1,280개는 상태 1,024 + 128 + 128인데, 그 두 128이 무엇인지와 경로 문맥이 25개
출력에 공통인지 출력마다 다른지가 **가중치만으로는 갈리지 않는다**. 두 읽기 모두 모든 텐서를
정확히 한 번씩 쓰고 서로 다른 답을 낸다. 확인할 수 없는 상태에서 하나를 고르면 아무도
검증할 수 없는 숫자가 나오므로, 목록에 올리고 빈칸을 적은 채로 둔다.

**열리는 조건**: 원 프로젝트의 `RouteMlpTrajectoryRegressor` 구현, 또는 확인용 (상태, 경로,
출력) 예제 한 쌍. 둘 중 하나면 된다.

학습 당시 점수는 카드에 적혀 있다. 10초 모델이 평균 3.14 m, 90초가 46.9 m, 240초가 115.8 m.

### 임무를 모델 입력으로

`digital_twin/simulation/uam_route_features.py`가 비행계획의 회랑을 그 모델들이 요구하는
형태로 바꾼다. 이 부분은 만들어졌고 실제 비행계획으로 확인했다.

- **경로**: 남은 구간을 기체 기준 body 좌표로, 구간마다 13개 값(끝점 상대위치, 방향, 길이,
  누적거리, 다음 회전, 마지막 구간 여부). 시간 범위 × 목표속도만큼 자르되 경계를 걸친
  구간은 남기고, 최대 48구간에 나머지는 0으로 채운다.
- **다음 waypoint는 가장 가까운 구간으로 정한다.** 두 점 중간에 있으면 앞의 점이 몇 미터
  더 가까울 수 있어, 점 기준으로 고르면 향하고 있던 waypoint를 건너뛰고 모서리를 자른다.
- **상태 21개** 중 위치·기수·속도는 엔진이 주고, 자세와 각속도는 날고 있는 경로에서,
  제어기 목표는 구간 속도와 다음 waypoint에서 나온다.
- **횡방향 오차는 0이다.** 실제 제어기가 선에서 벗어났다 돌아오는 데서 생기는 값인데
  우리 엔진은 회랑 위를 정확히 난다. 엔진에 대한 사실이지 비행에 대한 사실이 아니며,
  감추지 않고 함께 보고한다. 학습 자료와 다른 점이므로 모델이 돌게 되면 여기부터 본다.

자세한 근거는 ADR 0040.

### AI 모델 라이브러리

모델은 콤보박스가 아니라 **창에서 고른다**. 카드의 모델 버튼을 누르면 `AI 모델 라이브러리`가 열리고, 그 자리에서 쓸 수 있는 모델이 한 장씩 나온다. 각 카드는 아키텍처 그림의 AI Model Library와 같은 열(기능 · 적용 대상 · 시간 범위)을 쓰고, 종류(**규칙 기반** / **학습 모델** / **연동**), 무엇을 하는지, **필요한 입력**, 그리고 지금 쓸 수 있는지를 적는다.

- 쓸 수 없는 모델도 숨기지 않고 이유와 함께 보여 준다. 예: GRU는 "정규화 값(normalization.json)이 없어 예측을 실행하지 않습니다"로 `사용 불가`.
- 고르면 창이 닫히고 카드의 버튼이 바뀐다. 다른 설정과 마찬가지로 **적용**을 눌러야 저장된다.
- 예측 모델을 골랐는데 그 대상에 쓸 수 없으면(예: 5 Hz 이력이 필요한 모델 + 45초 간격 공급자 관측) 아무것도 그리지 않고 카드가 이유를 말한다.

### 화면에 그려지는 예상 경로

- 예상 경로는 **호박색 점선**이고, 위성 궤도(하늘색 실선)와 절대 섞이지 않는다.
- 선은 **매 프레임 기체를 따라 미끄러진다.** 서버에서 새 경로를 받는 것은 4초마다지만, 그 사이에도 코가 기체에 붙어 있고 앞끝이 계속 나아간다. 서버가 표시 구간보다 8초를 더 계산해 보내 주기 때문에 다음 수신 전에 앞끝이 마르지 않는다. 새 경로를 받아도 화면에서 튀지 않는다(실측 이동 0.00 m).
- 서버가 잠시 경로를 주지 못하면(관측이 늙어 추정 유효 한계를 넘음) 이미 받아 둔 경로를 기체가 지나칠 때까지 그대로 두고, 다 지나치면 사라진다. 예전처럼 4초마다 깜빡이지 않는다.
- 선택 패널의 `예상 경로` 상자가 모델·구간·예상 이동 거리·선회율·기준 관측 경과를 적고, 제출된 비행계획이나 측정된 궤적이 아니라고 밝힌다.
- 경로는 **추정 유효 한계(관측 + 60초)에서 잘린다.** 이미 그 한계를 넘긴 기체는 경로가 없다. OpenSky 관측은 보통 15~45초 늦게 도착하므로 실제로 보이는 창은 대개 15초 안팎이다.
- 모델 교체와 on/off는 재시작 없이 다음 tick부터 적용된다. 결정은 Library 설정에 저장되어 같은 대시보드를 보는 모든 화면이 같은 추정을 본다. 자세한 근거는 ADR 0034.

## 전달받은 학습 예측 모델

외부에서 받은 학습 모델은 `digital_twin/model_library/prediction_models/<model_id>/`에 원본 그대로 두고, 옆에 `manifest.json`(가중치에서 복원한 구조, 입출력 계약, SHA-256, 빠진 것)을 함께 둔다.

- **실행 가능 여부는 파일이 정한다.** `normalization.json`이 없거나 값이 비어 있으면 모델은 목록에 보이되 실행되지 않고, 이유를 말한다. 추측한 상수로 채우지 않는다 — 미터가 아닌 숫자로 경로를 그리면 틀린 답을 자신 있게 그리는 셈이다.
- **추론은 numpy로 한다.** GRU는 976 KB라 PyTorch를 얹지 않고 safetensors를 직접 읽어 계산하며, PyTorch와 대조해 못 박았다(최대 오차 5.7e-07).
- **입력은 리샘플하지 않는다.** GRU 계약은 0.2초 간격 16점(5 Hz)이다. 25~45초 간격으로 오는 공급자 관측을 보간해 5 Hz인 척 넣지 않고 거절한다.
- **채점 도구**: `python project_support/tools/evaluate_prediction_model.py [--run <id>] [--search-scale]`. 우리 UAM 비행 기록(5 Hz)의 창을 잘라 예측과 실제를 비교해 ADE·FDE를 내고, 같은 창에서 등속 외삽 점수를 함께 보여 준다.

지금 연결된 것은 `gru_direct_v1_1`(최근 3초 → 앞 15초)이며 정규화 값이 오면 바로 동작한다. UAM short/mid/long은 조사만 했다. 자세한 내용은 ADR 0036.

## Simulation: 하루치 비행계획 재생

`Simulation → UAM → 비행 계획 → 다중 비행` 카드 아래 `비행계획 불러오기 (CSV)`가 있다.
외부에서 받은 하루치 계획서를 그대로 올리면 읽어서 하루를 세우고, `Control Panel 열기`를
누르면 트윈이 그 날짜로 옮겨 간다.

### 계획서에 무엇이 있어야 하나

한 줄이 한 편이다. 반드시 있어야 하는 열은 편명(`flight_plan_id`), 기체(`aircraft_id`),
좌석과 탑승객(`seat_capacity`, `passenger_count`), 출발·도착 버티포트, 출발·도착 주기장과
FATO, 밀어내기 시각(`off_block_time`), 상태(`flight_status`). 나머지 시각 열(이륙·인계·
착륙·도착·정비완료)은 있으면 쓰고 없으면 없는 대로 둔다.

- 시각은 그 날짜의 현지 시계다. 자정을 넘어가면 다음 날로 이어 읽는다. 다만 **조금**
  거꾸로 간 값은 자정이 아니라 오타로 보고 앞 시각에 맞춘 뒤 알려 준다. 반나절 넘게
  거꾸로 가야 자정으로 친다.
- 배치되지 않은 버티포트로 가는 편은 **이름을 대며 거절한다**. 그 판을 놓고 다시 올리면 된다.
- 착륙 시각이 없는 편(`arrival_unresolved`)은 버리지 않는다. 계획을 만든 쪽에서도 도착을
  정하지 못한 편이고, 재생하면 PSU가 순서를 정한다. 받은 947편 중 26편이 그렇다.

### 좌석 등급과 3D 모델

| 좌석 | 기체 | 그리는 길이 | 순항 |
| --- | --- | --- | --- |
| 2인승 | Joby S4 | 8 m | 50 m/s |
| 4인승 | AirTaxi (기준 기체) | 11 m | 45 m/s |
| 6인승 | KP-2A | 13 m | 43 m/s |
| 8인승 | EVTOL | 15 m | 40 m/s |

기체는 **크기를 보고 고른 대역**이며 운항사가 그 제작사 기체를 쓴다는 뜻이 아니다.
취득한 모델들은 저작자가 남긴 크기 그대로라 실제 치수가 제각각이고(하나는 끝에서 끝까지
1.4 m다), 그대로 그리면 8인승이 2인승의 5분의 1로 보인다. 그래서 등급별 길이로 맞춰
그린다. 화면에 한 번에 뜨는 모델은 최대 16개이고 나머지는 점으로, 멀면 점도 화면 격자
단위로 솎아 낸다. 84대를 띄워도 프레임이 끊기지 않는 것은 이 예산 덕분이다.

### 경로: 그린 항로가 있으면 그것, 없으면 직항 회랑

그려 둔 항로망은 버티포트 306쌍 중 14쌍만 잇는다. 계획서는 그 밖의 쌍도 부르므로,
없는 구간은 **직항 회랑**을 만들어 난다. 상승 → 순항 → 강하 세 구간이고, 순항 고도는
항로망이 이미 쓰는 305 m·457 m AGL 두 층을 방향으로 나눠 쓴다(마주 오는 회랑이 500 ft
떨어지게). 만들어 낸 회랑이라는 사실은 콘솔 요약(`직항`)과 편별 CSV(`direct_corridor`)에
남는다. 항로를 더 그리면 그만큼 직항이 줄어든다.

### PSU: 누가 먼저 내리고, 누가 기다리나

착륙 3분 전에 조종사가 PSU에 요청하면 **착륙 번호**와 착륙 가능 시각을 받는다. 규칙은
선착순이다.

- 한 판은 착륙 사이에 90초, 출발 사이에 60초, 착륙과 출발 사이에 75초를 둔다.
- 먼저 요청한 편은 밀리지 않는다. 뒤에 온 편이 그 앞 빈 자리에 통째로 들어맞으면
  기다리지 않고 먼저 내린다.
- 도착 주기장이 차 있으면 빈 자리로 바꿔 주고, 판 전체가 차 있으면 기다린다.
- 30분을 넘겨야 하는 편은 회항 후보로 보고하고 그 자리를 잡지 않는다.

기다려야 하는 편은 **강하를 시작할 지점에서 역천이하고** 회랑 밖으로 나간다. 대기점은
그 버티포트의 항로·이륙 경로에서 35° 이상 떨어진 방위 중 비어 있는 곳이고, 이미 누가
기다리고 있으면 다른 방위 또는 120 m 위층을 쓴다. 대기가 짧으면 반경도 줄인다(최소
400 m) — 1.5 km를 왕복하는 데 대기 시간보다 오래 걸리면 기다린 게 아니라 다녀온 것이다.
대기 시간은 전부 기록되며 나중에 시각화할 자료다.

**아직 없는 것**: 공중 충돌·분리 판정. 판 단위 시간 분리와 직항 회랑의 방향별 고도만
있고, 두 기체가 공중에서 가까워지는 것은 보지 않는다.

### 버티포트별 수요 비율

하루 수요를 판별로 나누는 값이다. 편성하는 쪽이 쓰는 식은 판마다 출발 비율과 도착 비율
두 개를 요구하고, 이 단계가 그것을 만든다.

숫자는 **평균 버티포트 대비 비율**이다. 100%가 평균이고, 강남이 210%, 용산이 50%다.
10% 단위로 올리고 내리며 범위는 0%~300%. 0%로 두면 그 판은 출발(또는 도착)하지 않는다.

- **기본값은 받은 자료다.** 서울시 통행 수요의 출발·도착 비율(원본은
  `digital_twin/model_library/demand_reference/`)을 평균 대비로 환산한 값이다. 손대지
  않은 판은 그 값을 그대로 나르므로, 자료가 갱신되면 저절로 따라간다.
- **자료에 없는 판은 추측하지 않는다.** 인천에는 대응하는 행이 없어 100%에서 시작하고,
  그 숫자가 예측이 아니라 우리가 놓은 값임을 표시한다.
- 각 행의 작은 글씨는 그 판이 **지금 선택된 판들 사이에서** 차지하는 몫이다. 한 곳을
  올리면 다른 곳의 몫이 함께 줄어든다. 비율이기 때문이다.
- `기본값 (받은 자료)`는 손댄 것을 모두 되돌리고, `모두 100%`는 분배를 평평하게 만든다.

받은 자료의 17행은 합이 1이 아니라 0.803이다. 나머지는 버티포트를 놓지 않은 지역의
몫이므로, 이 값들을 확률로 쓰지 않고 **가중치**로 쓰고 실제 비율은 선택된 판들 사이에서
다시 정규화한다. 자세한 근거는 ADR 0039.

### 생성 요약

`생성 요약`을 누르면 설정 패널 바로 옆에 요약 창이 열린다. 지도 건너편이 아니라 옆이라,
숫자를 고치고 그것이 하루에 무엇을 했는지 보는 것이 한 번의 짧은 시선으로 끝난다.
설정 서랍을 여닫으면 창도 같이 따라 움직인다.

| 자리 | 내용 |
| --- | --- |
| 위 네 칸 | 하루 수요 · 버티포트와 연결 쌍 · 운영 시간과 시드 · 배치 기체와 좌석 |
| 버티포트별 수요 분배 | 판마다 출발·도착 막대. 많이 맡는 순서이고, 조정한 곳은 표시된다 |
| 수요가 많은 구간 | 두 비율로 계산한 상위 8개 구간과 예상 인원 (참고 추정) |
| 초기 배치와 좌석 공급 | 운영 시간 동안 실을 수 있는 좌석과 하루 수요의 대비 |

아래에 `JSON 내려받기` · `생성 요청` · `닫기`가 있다. 요청할 수 없는 설정이면 맨 위에
이유가 나오고 `생성 요청`은 잠긴다.

설정 파일(JSON)은 이 창에서만 받는다. 같은 문서를 폼 아래 버튼으로도 내주면 그것이 무엇을
담고 있는지 말해 주는 곳에서 멀어진다.

**요청에 실리는 것**: 가중치(`weight_pct`)와 그것을 정규화한 비율(`share`)을 판마다 함께
담는다. 편성 계산은 받는 쪽에서 하며, 이 패널은 값을 모아 전달만 한다.

### Control Panel

`Control Panel 열기`를 누르면 지도 아래에 콘솔이 뜨고 **트윈이 그 날짜로 옮겨 간다**.
그 위의 위성도 그 날의 위성이고, 창밖을 날고 있는 실시간 항공기는 그리지 않는다.
상단 시계에도 `· 재생`이 붙는다. 실시간 수집은 그동안에도 계속 돌고 저장되며, 다만
화면에 나오지 않을 뿐이다.

| 자리 | 뜻 |
| --- | --- |
| 시계 · 진행 막대 | 하루 중 어디까지 왔는지 |
| 운항 중 · 주기 | 비행 중인 기체(지상이동 포함)와 판 위에 선 기체 |
| PSU 대기 | 지금 기다리는 기체와 누적 대기 건수 |
| 완료 · 탑승객 | 도착한 편과 지금 기내에 있는 인원 |
| 평균 대기 | 대기한 편의 평균과 최대 |
| 재생 · 일시정지 · 중지 · 초기화 | 중지는 기록을 파일로 남기고, 초기화는 순서까지 잊는다 |
| ×1 ~ ×10 | 배속. 일시정지 중 흐른 시간은 나중에 몰아 흐르지 않는다 |
| 캡쳐 · 녹화 | 지금 지도 화면을 PNG로, 또는 다시 누를 때까지 WebM으로 |

일시정지는 **시계를 멈추는 것이지 조종사에게 대기를 지시하는 것이 아니다.**
초기화는 하루를 처음으로 되돌리고 PSU가 준 착륙 번호까지 잊는다. 이미 4번을 받은
기체에게서 번호를 도로 빼앗을 수는 없으므로, 시계를 뒤로 감는 방법은 초기화뿐이다.

### 사람이 타고 내린다

하루 재생에서도 **비행계획에 배정된 인원만큼** 사람이 걸어서 타고 내린다. 출발 판에서는
기체가 게이트에 서 있는 동안 대기소에서 나와 한 명씩 탑승하고(그 시간만큼 지상 이동이
늦춰진다), 도착 판에서는 착륙해서 게이트에 든 뒤 한 명씩 내려 대기소로 걸어 들어간다.
**마지막 한 명이 내리기 전에는 회항 준비가 끝나지 않는다.**

동선과 시간표는 계획이 그린 것이고, 하루는 그것을 재생만 한다. 걷는 사람 수는 그 편의
배정 인원이다 — 8인승에 6명이면 6명이 걷는다.

최적화: 서버는 **지금 걷고 있는 기체만** 답하고(붐비는 아침에도 스무 대 남짓), 화면은
**카메라에서 가까운 판부터 정해진 수의 몸만** 그린다(28개, 900 m). 열여덟 개 판이 동시에
붐벼도 그리는 비용은 한 판과 같다. 몸은 한 번 만들어 계속 돌려 쓰므로 붐비는 판이 바뀌어도
다시 불러오지 않는다.

### 남는 기록 (Library → 다운로드)

| 파일 | 내용 |
| --- | --- |
| 편별 결과 (CSV) | 편마다 한 줄. 계획된 출발·착륙 시각과 실제 시각, 그 차이, 착륙 번호, 대기 시간, 직항 여부 |
| 항적 (JSONL) | 비행 중인 기체의 1초 간격 위치·고도·기수·속도와 비행 단계. 한 줄에 한 표본 |
| PSU 대기 (JSON) | 기다린 편마다 어느 판에서 몇 번으로 얼마나. 통계 포함 |

재생 중에 내려받아도 된다. 그 순간까지의 전부가 나온다.

### 비행체를 누르면: 임무 상태

재생 중인 UAM을 고르면 정보 패널 안에 **임무 상태**가 하나 더 붙는다. 트윈의 엔티티는
위치와 자세만 알고, 그 기체가 지금 무엇을 하는 중인지는 하루를 돌리는 쪽만 안다. 그래서
고른 동안 1.5초마다 물어보고, 고름을 놓으면 묻기를 멈춘다. UAM이 아닌 대상에는 붙지 않는다.

| 줄 | 내용 |
| --- | --- |
| 임무 상태 | 대기 중 · 출발 준비 · 이륙 · 상승 · 순항 · 접근 · 체공 진입 · 체공 · 접근 재개 · 착륙 · 도착 |
| 비행 단계 | 위 상태를 만드는 계획의 단계 (`gate_out`, `hold_exit`, `landing` …) |
| **비행 모드** | 지상 · 멀티로터 · 모드 전환 (천이) · **고정익** |
| 편명 · 구간 | 지금 수행 중인 편과 출발·도착 판 이름. 서 있는 기체는 대신 주기 위치 |
| **비행 진행률** | 막대와 퍼센트, 착륙까지 남은 분. 막대 위의 옅은 선이 계획상 지금 있어야 할 위치 |
| **계획 대비** | `계획대로 (+12초)` / `3분 늦음 (+184초)` / `1분 빠름 (-71초)` |
| 좌석 · 탑승 | 좌석 수와 **지금 타고 있는** 인원 |
| **탑승 · 하기** | 걷는 중일 때만. `2 / 4명 (50%)` |
| 대지 속도 | m/s와 kt를 같이. 날고 있을 때만 |
| **로터 Tilt** | 0°가 멀티로터, 90°가 고정익. 비행 모드와 같은 숫자 |
| 착륙 순번 · PSU 응답 | PSU가 번호를 준 뒤부터 |
| 대기 시간 | 그 편이 기다린 누적 시간 |
| 경로 | 설계 항로가 없어 직항 회랑을 쓰는 편에만 |
| **지도 표시** | `지나온 항적 240점 · 예상 경로` — 지금 지도에 무엇이 그려져 있는지 |
| 남은 편수 | 그 기체가 오늘 더 할 편 수 |

체공 중이면 상자에 표시가 붙고 **항로 밖에서 기다리는 중**이라고 적는다. 어느 줄에도
관측이라는 말은 쓰지 않는다 — 아래 주석이 매번 시뮬레이션 결과임을 말한다.

### 지나온 항적

UAM을 고르면 **그 편에서 지나온 길**이 초록 실선으로 지도에 그려진다. 앞으로 갈 길(예상
경로, 주황 파선)과 다른 층이라 둘이 한 화면에 같이 뜬다. 항적은 **편에 속한다** — 다음 편이
시작되면 처음부터 다시 그리고, 방금 착륙한 기체를 누르면 어디서 왔는지가 그대로 남아 있다.

40 m 또는 4초마다 한 점, 한 편당 900점까지. 대기 중에 같은 자리가 버퍼를 채우지 않게 하고,
고른 동안 3초마다 갱신한다. 내려받는 항적 파일(`tracks.jsonl`)은 이것과 별개로 기록기가 쓴다.

### 비행 모드와 순항

계획의 각 단계는 로터를 어디로 향하는지 함께 들고 있고, 조종사가 실제로 나는 동안에는 계측된
tilt가 그 자리를 대신한다. 그래서 **화면의 말과 화면의 모델이 어긋날 수 없다**.

| 단계 | 모드 |
| --- | --- |
| 지상 이동 · 주기 · 충전 | 지상 |
| 수직 이륙 | 멀티로터 |
| 상승 | 모드 전환 (천이) |
| **순항** | **고정익** |
| 강하 | 모드 전환 (천이) — 접근 **전에** 끝난다 |
| 체공 진입 · 체공 · 접근 재개 | 멀티로터 |
| 착륙 | 멀티로터 |

회랑의 꺾이는 점은 **지나간다**. 예전에는 경유점마다 역천이하고 3 m/s 아래로 감속했다가 다시
전환해서, 비행 한 편에 모드가 평균 **28번** 바뀌었다. 지금은 **4번**이다(같은 30편 비교).

대신 코너를 조금 자른다. 회랑 폭 300 m에 우측통행 오프셋 30 m이므로 그만큼 여유가 준다 —
정확도보다 부드러움을 택한 것이고, 충돌 회피는 어차피 아직 없다.

**날개가 날기를 멈추면 로터가 되찾는다.** 실속 속도(45 kt) 아래에서 가라앉고 있으면 경로가
무엇을 원하든 로터로 돌리고, 다시 날개가 실어 나를 수 있는 속도가 될 때까지 가지고 있는다.
이것이 없으면 꺾임점을 통과하는 기체가 상승 꼭대기에서 실속해 지면까지 떨어진다 — 계측했다.

이 동작은 **하루 재생 모드에만** 걸린다. 단일 비행(`단일 비행` 탭)은 손대지 않았다.
자세한 근거와 계측값은 ADR 0043.

우측통행은 순항 구간에서 회랑 중심선 오른쪽 30 m다. 200 m에 걸쳐 진입·이탈하므로 이착륙
경로와 이어지는 부분에서 튀지 않고, 반대 방향 교통과는 그만큼 떨어진다.

### Stakeholders에서 보이는 것

재생 중에는 이해관계자 화면 맨 위에 **이 화면은 시뮬레이션입니다**가 날짜·파일·시계와
함께 뜬다. 실시간 화면과 똑같이 생긴 화면을 보고 판단하는 일이 없게 하기 위한 것이다.
`버티포트` 탭에서는 그 아래에 고른 판의 실시간 상태가 붙는다 — 주기·접근·대기·출발 수와
기다리는 기체(착륙 번호와 대기 시간), 판 사용 예정.

### 조종사 화면: 운항 속도

`Stakeholders → 조종사`에 **운항 속도**가 있다. 비행 계획을 어떤 속도로 나는지를 정하는
자리이고, 정하는 것은 속도뿐이다. 어디로 가고 얼마나 높이 나는지는 배정받은 항로가
정하고, 조종사는 그 항로를 따라 오르내린다.

| 항목 | 기본값 | 쓰이는 곳 |
| --- | --- | --- |
| 지상 이동 (출발) | 2.6 kt | 게이트 → FATO |
| 지상 이동 (도착) | 3.0 kt | FATO → 게이트 |
| 수직 속도 (이륙) | 500 ft/min | 이륙 상승 |
| 수직 속도 (착륙) | 300 ft/min | 착륙 강하 |
| 순항 속도 | 130 kt | 순항 구간 |
| 실속 속도 (기체 값) | 45 kt | 천이 속도의 밑값 |
| 천이 계수 | 1.2 | 실속 속도에 곱해 천이 속도 |

천이 속도는 `1.2 × Vstall = 54 kt`이고, 상승·강하는 천이와 순항의 사이(92 kt)로 난다.
실속 속도만 우리 기체 값이라 화면에 `기체 값`이라고 적어 둔다 — 나머지는 받은 운항 수치다.
아래에는 단계별 속도가 kt/ft·min과 m/s 두 단위로 같이 뜨므로 머릿속에서 환산할 일이 없다.

바꾼 값은 서버에 남고, **그 뒤에 만드는** 비행 계획부터 적용된다. 이미 재생 중인 하루는
그대로 간다. `기본값` 버튼이 받은 수치로 되돌린다.

같이 받았던 임무 프로파일 표(단계별 고도와 절차)는 쓰지 않는다. 옛 자료이고, 고도는 지면
고도와 설계한 항로가 이미 가지고 있다. 화면에도 그렇게 적혀 있다.

### 한계

- 불러온 하루는 메모리에만 있다. 서버를 다시 켜면 다시 불러와야 한다(기록 파일은 남는다).
- 시각을 되감을 수 없다. 되돌리려면 초기화하고 다시 재생한다.
- 위성을 계획 날짜로 전파하면 TLE 기준일에서 멀어질수록 오차가 커진다. 하루 앞뒤는
  문제없지만 몇 달 뒤 날짜의 하늘은 참고용으로 본다.

자세한 근거는 ADR 0038.

## Library: 자료 공급자 상태와 수집 설정

- rail의 Library 패널에 항공기·위성·UAM·지형·건물 층이 있다. 기본은 모두 접힘이고, 머리글을 누르면 그 자료의 설정만 펼쳐지고 다시 누르면 닫힌다. 접힌 상태에서도 머리글에 공급자와 현재 상태가 보인다. 각 카드는 공급자와 지금 상태(수신 중, 저장 자료 사용, 연결 실패와 이유, 수집 중지 등)를 보여 주고, 그 자료에 필요한 설정을 바로 고칠 수 있다.
- 기상(Open-Meteo): 수집 켜기/끄기, 수신 주기(300초~24시간). 인증키 없이 현재 수신 범위의 중심과 네 모서리를 한 번의 요청으로 받아 구름량·시정·바람·기온을 얻는다. `GET /api/live/weather`로 마지막 관측을 읽는다.
- 구름 영상(NASA GIBS): 표시 켜기/끄기, 자료(기본 Himawari 적외 10분 주야 · Himawari 가시 10분 주간 · MODIS 구름량 전 지구 일별), 진하기, 갱신 주기. 어느 자료든 회색으로 만들고 어두운 쪽을 걷어내 지도 위에 흰 구름만 남긴다. 정지궤도 자료는 위성이 보는 범위 밖 타일을 요청하지 않는다. 설정 패널의 구름 토글과 같은 값이며 어느 쪽을 눌러도 함께 움직인다. 브라우저가 타일을 직접 받으므로 켜야 요청이 나간다.
- 항공기(OpenSky): 수집 켜기/끄기, 수신 주기(30~3600초), 상태 보관(60~3600초), 지도 화면 따라가기, 수신 범위(위경도, 한 변 0.05~25°). 화면 따라가기를 끄면 설정한 범위로만 받는다.
- 위성(CelesTrak): 실시간 요청은 기본 꺼짐이며 저장된 궤도로 계산한다. 켜면 주기(1~24시간)대로 요청한다.
- 지형·건물: 표시 켜기/끄기. 저장되고 다음에 열 때도 그대로 적용된다. UAM은 실시간 공급자가 없어 상태만 보여 준다.
- 하한은 공급자 보호다. 더 잦은 요청은 서버가 422로 거부하고 어떤 항목이 왜 잘못됐는지 알려 준다. 적용은 다시 실행하지 않아도 다음 수집 주기부터 반영되고, 설정은 `data/workspace/settings/sources.json`에 저장된다. API는 `GET/PUT /api/library/sources`이다.

## 접속 연출

- 로딩이 100%에 닿으면 바로 사라지지 않는다. 완료 문구를 0.9초 보여 준 뒤 지도에 넘기고, 그때 카메라가 지구 전체가 보이는 약 21,700 km 상공(한반도 남서쪽)에 놓여 6.4초 동안 서울 상공 120 km까지 한 번에 내려온다. 로딩 화면은 그 위에서 0.9초 동안 옅어지며 살짝 확대돼 걷히므로, 걷히는 순간 지도는 이미 움직이고 있다.
- 지도를 잡으면(포인터 조작) 비행은 즉시 멈추고 그 자리에서 조작이 이어진다. 운영체제의 동작 줄이기(`prefers-reduced-motion`)에서도 연출은 사라지지 않는다. 지구에서 내려오는 것은 그대로 두고 옆으로 도는 움직임만 빼서 정면으로 4.2초에 내려오며, 로딩 화면은 확대 없이 0.38초 동안 옅어진다.
- 연출은 `digital_twin/visualization/web/entry_flight.js`가 계획하고 `LiveGlobe.entry()`가 실행한다. 데이터나 타일과는 무관하며 카메라만 다룬다.

## 항공기 움직임 연속성

- Live Twin은 마지막 관측 위치·속도·진행 방향으로 관측 사이를 잇는다. 추정은 관측 후 `max_extrapolation_seconds`(60초, `motion_models/catalog.json`) 동안만 이어지고 그 뒤 위치를 고정하며 `stale`로 표시한다. 실측 OpenSky 수신 주기 약 25초와 수신 시점 노후도(최소 약 13초), 한 번의 수신 누락까지 덮는 값이며 무한정 늘리지 않는다.
- 새 관측은 3초 시간상수로 점진 보정한다. 관측 간격이 75초를 넘는 장기 단절이나 속력·간격에 비해 큰 위치 오류만 `discontinuity`로 처리하고 `continuity_id`를 올린다. 플래그는 해당 tick에만 남는다. 진행 방향은 359°→1°처럼 짧은 호로 잇고, 기체 자세가 아니라 ground track이다.
- 상세 패널은 관측 시각, 수신 시각, 상태 시각, 관측 경과, 추정 유효 한계를 구분해 보여 준다.
- `/ws/live`는 새 상태가 생길 때 한 번만 보낸다. `stream_seconds`는 최소 전송 간격이며 같은 상태를 반복 전송하지 않는다(keepalive는 10배 간격).
- 브라우저는 최근 상태 샘플 사이만 보간한다. 최근 도착 간격과 지연 변동에 맞춘 0.5~5초의 표시 버퍼로 불규칙한 도착을 흡수하고, 최신 상태를 넘어 외삽하지 않으며, 뒤로 움직이지 않는다. 10초 이상 공백(숨긴 탭 복귀, 서버 재시작)은 재동기화한다. 모델·선택 대상·근접 대상은 매 프레임, 먼 점은 기존 주기로 갱신한다.
- `http://127.0.0.1:8766/?diagnostics`로 열면 `globalThis.aerodtDiagnostics`(globe, client, samples, timing)가 노출된다. 검증 도구 전용이며 화면 기능에는 쓰지 않는다.

## 3D 건물과 조명

로컬 Cesium 인증정보를 준비했다면 기존 실행 명령에 `--buildings`를 추가한다.

```powershell

```

- 인증은 `AERODT_CESIUM_ION_TOKEN` 환경변수 또는 저장소 밖 `%LOCALAPPDATA%/AeroDT/credentials/cesium.json`의 `accessToken`을 사용한다. 계정 토큰은 서버에만 보관한다. 키 점검과 복구는 아래 `인증 키 관리`를 따른다.
- 브라우저는 같은 출처의 `/api/visualization/buildings/endpoint`에서 건물 자산에 제한된 임시 접근정보를 받는다. 고정된 Cesium OSM Buildings(96188)만 사용하며 사용자 지정 자산 프록시가 아니다.
  - 실제 카메라 고도 6.5 km 이내에서 최초 연결하고, 8 km 이상에서 숨긴다. 위성 추적 거리와 혼동하지 않는다. 카메라 주변 2 / 3.5 / 5 km 범위와 실제 시야로 타일 요청을 제한한다. GPU 캐시 목표는 프로필별 96 / 192 / 256 MiB, 추가 허용량은 64 MiB다. 현재 화면을 덮는 큰 타일 때문에 순간 초과할 수 있는 소프트 예산이며 절대 상한은 아니다. 대상을 추적하는 동안에도 타일 요청을 멈추지 않는다.
- 우측 건물 버튼으로 독립적으로 숨길 수 있다. 실패하더라도 지구와 Live Twin은 계속 작동한다. OSM 건물은 지역별 범위와 높이 정확도가 다르며 사진 실사 모델이 아니다.
- 우측 ☀ 버튼: 켜짐은 시스템 현재 시간의 낮/밤 조명, 꺼짐은 지구 전체를 은은하게 표시한다. 해를 끄면 지도 밝기/감마를 올린 전용 설정을 적용하고, 켜면 기존 설정으로 돌아간다. 물리 상태나 Live Twin 시간은 변경하지 않는다.
- 별은 성긴 장식용 skybox이며 실제 별자리 또는 천문 관측 자료가 아니다. 별용 외부 API 요청은 없다.
- Cesium ion과 OpenStreetMap 출처 표시는 숨기지 않는다. 현재 계정의 상업 사용 안내도 공급자가 내려준 그대로 표시한다.

## 지도 자료 선택: 브이월드 영상과 건물

설정(⚙) 패널의 "지도 표시"에서 영상, 건물 자료, 건물 범위, 건물 진하기를 고른다. 선택은 Library 설정과 같은 저장소에 남으므로 같은 대시보드를 보는 모든 화면이 같은 지도를 본다. 기본 공급자는 지금까지의 자료다. 펼친 메뉴도 어두운 배경에 밝은 글자로 표시한다.

| 행 | 선택지 | 비고 |
| --- | --- | --- |
| 지도 영상 | Esri World Imagery(기본) · 브이월드 위성영상 · 위성 + 지명 · 일반지도 · 야간지도 | 브이월드 영상은 국내(레벨 6~19)만 덮고, World Imagery **위에** 얹히므로 밖은 그대로 보인다. |
| 건물 자료 | Cesium OSM Buildings(기본) · 브이월드 건물 · 브이월드 정밀 3D(실사 텍스처) | 압출 건물은 도형을 실측 높이(없으면 층수×3.3 m, 그것도 없으면 3 m)로 세운다. 정밀 3D는 원본 외벽, 지붕 사진과 입체 형상을 사용한다. 지역별 구축 범위와 제작 시기가 다르다. |
| 건물 표시 거리 | 자동 8~40 km · 주변 8 km · 도시 20 km · 광역 40 km | 화면이 향하는 지표 주변의 최대 반경이다. 자동은 높이에 따라 점진적으로 넓어진다. 줌아웃 시 레이어를 끄지 않고 먼 건물은 낮은 상세도와 안개로 처리한다. 도시/광역은 OSM 또는 정밀 3D를 사용한다. |
| 건물 상세도 | 가볍게 96 MiB · 균형 192 MiB · 정밀 256 MiB | 표시 거리와 독립인 타일 캐시 목표다. 64 MiB overflow와 큰 단일 타일에 따른 일시 초과가 가능하며 전체 앱/GPU 메모리의 절대 상한은 아니다. |
| 건물 진하기 | 기본 90%, 35~100% | 단색 건물은 차분한 청회색이며 매끄러운 알파 투명도를 사용한다. 실사 모델은 90% 이상에서 선명한 불투명 경로를 쓰고, 그 아래에서는 사진 가독성을 위해 8%p 더 진하게 표시한다. 투명 모드는 GPU 합성 비용이 더 들므로 성능 우선이면 100%를 고른다. |

- 브이월드 **영상과 압출 건물**에는 키가 필요하다(`vworld.json`, 아래 `인증 키 관리`). 키는 서버에만 있고 브라우저는 같은 출처의 `/api/visualization/vworld/tiles/...`와 `/api/visualization/vworld/buildings/{column}/{row}`만 부른다. **공개 정밀 3D**는 별도 TDServer에서 제공하므로 이 키를 보내지 않는다. `/api/visualization/vworld/3d/...`는 고정된 공급자 경로만 중계하며 외부 URL과 경로 탈출을 거부한다.
- 압출 건물은 0.01° 셀로 받아 서버 메모리에 6시간, 최대 160셀을 보관한다. 브라우저는 지표 초점 주변 32/48/64셀, 보관 목표 80셀, 동시 2셀, 전체 18,000동과 원본 정점 260,000개의 예산을 쓴다. 보이는 셀 전체에 예산을 나누며 셀당 높은 건물부터 최대 1,800동만 세운다. 광역 전체를 채우기 위해 Data API 요청을 무한히 늘리지는 않는다. 경계 건물은 중심이 속한 셀만 소유하며 지난 요청은 취소한다.
- 정밀 3D의 구형 CRN 압축 사진을 WebP로 변환한다. 원거리 REPLACE 부모 사진은 타일 전체 256 Ki pixels/개별 최대 256 px, 자세한 leaf와 ADD 모델은 기존 4 Mi pixels/개별 최대 1,024 px다. 거리 LOD가 바뀔 때 가까운 모델에 더 자세한 사진이 나타난다. 형상, 좌표와 실제 모델 LOD 의미는 그대로이며 content 없는 중간 노드의 종료 오차만 보정한다. WebP 품질 90의 손실 압축으로 원본 무손실 표시는 아니다.
- 정밀 타일 중계는 동시에 최대 8개 작업, 사진 변환 2개, 원본 응답 32 MiB와 서버 캐시 96 MiB를 제한한다. 실패는 60초 쉬고 같은 요청은 합친다. 변환한 공개 3D 타일은 worker에서 한 번 gzip 압축하고 그 결과를 공유한다. ETag 재검증에 일치하면 304이며 재압축하지 않는다. 공개 3D 결과만 `data/workspace/cache/vworld_3d`에 목표 256 MiB/2,048개/1시간으로 보관해 재방문과 재시작에 재사용한다. 키가 필요한 영상·공역·건물 셀은 이 저장소에 넣지 않는다. GPU 예산과 디스크 예산은 별개다.
- 카메라가 움직이면서 지속적으로 렌더 부하가 클 때만 drawing buffer를 85%, 최대 70%로 줄이고 정지 후 0.7초에 원래 해상도로 복구한다. 표시 거리와 원본 모델·사진을 줄이는 설정은 아니다. 이동 중 지도 라벨은 함께 리샘플링될 수 있으나 DOM 설정 메뉴는 그대로다. 정지한 시점은 지표 시야와 셀 선별을 재사용하고 지형이 바뀌면 갱신한다. ADR 0023에 조건과 한계를 기록했다.
- 공급자는 한 번에 하나만 표시한다. 숨긴 타일은 요청을 멈추고 오래된 캐시는 비운다. 지형 변경 때 압출 건물은 받아 둔 도형으로 다시 세우되 새 GPU 배치가 준비될 때까지 기존 배치를 유지한다. 멀리 있는 지형 타일 하나의 실패로 도시 전체를 숨기지 않는다.
- **지형은 여전히 Cesium World Terrain이다.** 정밀 건물용 TDServer와 이전에 닫혀 있던 XDServer DEM은 별개다. 지형의 도심 융기나 건물 바닥과의 높이 차이가 이 기능으로 해결되는 것은 아니다. ADR 0020과 후속 ADR 0021을 참고한다.

## 2D 지도 전환

우측 카메라 막대의 `2D` 버튼이 지구와 북쪽 위 2D 지도를 오간다. 전환은 세 단계다: 3D에서는 먼저 화면 중앙 지표 위로 카메라를 수직·북쪽 정렬로 옮긴 뒤(현재 거리 유지) Cesium morph를 실행하고, 2D에서 3D로는 곧바로 morph한다. 이렇게 하면 기울어진 시야 아래에서 지구가 펴지는 대신 수직 시야에서 평면으로 펼쳐지므로 전환이 매끄럽다. 전환 중 휠·드래그·홈·방향 버튼 입력은 무시되며 전환을 중간에 끊지 않는다(`completeMorphOnUserInput=false`). 새 전환 요청은 이전 요청을 대체한다.

- 2D에서는 회전·기울기가 잠기고 N/⊙ 버튼이 비활성화된다. 지도 폭이 3D의 카메라 거리 역할을 하며 휠, 슬라이더, 대상 보기(접근), 추적 모두 지도 폭으로 동작한다. Cesium은 수직 시야를 높이와 같은 폭의 지도로 넘긴다.
- 추적은 모드 전환을 넘어 유지된다. 2D에서는 대상을 중심에 두고 현재 폭을 유지하며, 3D로 돌아오면 같은 거리의 수직 시점에서 다시 궤도가 된다.
- 대상 표시 정책(점·모델·이름표 범위)은 2D에서 지도 폭을 고도로 삼아 적용된다. 3D 건물은 2D에서 명시적으로 숨기며 대상 위치는 지도 좌표로 투영해 판정한다.

## 원본 프로젝트 통합

실제 운용 및 개발 위치는 프로젝트 원본 폴더다. 최상위 main.py와 web_venv 및 웹 GUI 전체가 이 안에서 독립 실행되며 Codex 작업 폴더를 참조하지 않는다.

기존 수집 86개 자산의 catalog.json 및 visual_asset.schema.json은 보존한다. `model_library/visual_catalog.py`가 메타데이터를 읽어 렌더러용 응답을 만들며 public_export=false인 자산을 제외한다. 임시 두 모델은 visual_assets/procedural에 분리하고 procedural_catalog.json 및 procedural_visual_asset.schema.json을 사용한다. 원래 수집 자산을 임시 모델 목록으로 덮어쓰지 않는다.

## 지형 자료의 한계와 평면 지표 전환

Cesium World Terrain은 한국 지역에서 최대 level 13(약 30 m 격자, SRTM 2000년 기원)이며 평지에 ±4~10 m의 잡음이 있다. 실측(`sampleTerrainMostDetailed`): 인천공항 활주로 3 km 구간 18~33 m, 김포 32~50 m, 김해 29~41 m, 제주 37~52 m, 김제 평야 30~69 m, 2000년 이후 매립된 새만금은 23.4~23.5 m로 평탄(당시 바다). 따라서 확대 시 활주로가 굴곡져 보이는 것은 렌더링 오류가 아니라 자료의 한계이며, Cesium OSM 건물의 바닥 높이가 이 지형에 맞춰져 있어 지형만 다른 자료로 바꾸면 건물이 뜨거나 묻힌다.

브이월드로 지형을 바꾸는 것도 확인했으나(2026-09-09) 3D·DEM 서비스가 닫혀 있어 불가능하다. 영상과 건물만 브이월드로 바꿀 수 있다(`지도 자료 선택`).

우측 `▲` 버튼은 지형 기복을 끄고 평면 지표(타원체)로 전환한다. 이때 건물은 지형 gate에 따라 함께 숨겨진다(바닥 높이가 World Terrain 기준이므로 평면 위에서는 뜬다). 다시 켜면 보관해 둔 World Terrain 공급자를 그대로 복원한다. 근본 해결은 한국 DEM(국토지리정보원 5 m 등)으로 만든 지형 타일과 그에 맞는 건물 자료를 함께 도입하는 것이며, 별도 자료 작업이 필요하다.

## 항공기 요청 범위

OpenSky는 요청마다 과금하고 넓은 영역일수록 비싸다. 전 지구를 15초마다 요청하던 기존 기본값은 하루 예산을 몇 시간 만에 소진해 HTTP 429(측정: 잠금 잔여 18,081초)를 받았다. 현재 기본값은 한반도 상자(위도 33.0~38.6, 경도 126.0~130.0, 22.4 제곱도)와 45초 주기이며, 이 면적을 비싼 쪽으로 가정해도 하루 3,840 credit으로 인증 계정 한도 안에 들어간다.

화면이 보고되면 요청 범위는 그 화면을 따라간다. 브라우저가 보이는 지표 사각형을 `POST /api/live/view`로 알리고(같은 출처만 허용), 서버는 다음 규칙으로 실제 요청 영역을 정한다.

- 화면 밖에서 날아 들어오는 대상을 미리 확보하도록 1.35배 여유를 둔다.
- 가까이 확대해도 최소 0.5도는 요청해 주변을 함께 받는다.
- 면적이 최저 요금 구간(22 제곱도)을 넘으면 화면 중심을 유지한 채 축소한다. 따라서 요청 비용은 어디를 보든 일정하다.
- 위도나 경도 폭이 45도를 넘으면 특정 지역을 보는 것이 아니므로 설정된 한반도 상자를 그대로 쓴다. 지구 전체 시야에서 화면 중앙의 바다를 요청하는 일이 없다.
- 보고가 없으면(브라우저 미접속, 첫 기동) 설정 상자를 쓴다. 마지막 보고가 항상 이긴다.

브라우저는 4초에 한 번, 그리고 0.02도 이상 움직였을 때만 보고한다. 실패한 보고는 다시 보낸다. 전 지구를 다시 받으려면 `aircraft_bounds`를 `{}`로 두고 주기를 90초 이상으로 올린다.

## 인증 키 관리

키는 저장소 밖 한 곳에만 둔다: `%LOCALAPPDATA%\AeroDT\credentials\`.

| 파일 | 항목 | 없을 때 |
| --- | --- | --- |
| `cesium.json` | `accessToken` | 지형(DEM)과 3D 건물이 모두 꺼진 채 실행된다. 건물은 지형 준비를 기다리므로 확대해도 나오지 않는다. |
| `opensky.json` | `clientId`, `clientSecret` | 실제 항공기 수집만 꺼진다. |
| `vworld.json` | `apiKey` | 브이월드 영상과 압출 건물이 동작하지 않는다. 공개 정밀 3D는 별도 연결이다. 등록 도메인은 `default.json`의 `vworld_domain`이다. |

완전한 환경변수(`AERODT_CESIUM_ION_TOKEN`, `AERODT_OPENSKY_CLIENT_ID`/`_SECRET`, `AERODT_VWORLD_API_KEY`)가 있으면 파일보다 우선한다. 어느 쪽도 없으면 실행은 계속되고 해당 연결만 비활성화되며, launcher가 `로컬 인증정보 없음` 한 줄을 출력한다. 조용히 실패하지는 않지만 화면에서는 지형과 건물이 그냥 없는 것처럼 보인다.

현재 상태 점검(값은 출력하지 않고 길이와 지문만 표시한다):

```powershell
project_support\tools\credentials.ps1
```

키 복구 및 등록:

```powershell
project_support\tools\credentials.ps1 -CesiumFromUnrealConfig <Unreal 프로젝트>\Config\DefaultGame.ini
project_support\tools\credentials.ps1 -CesiumFromJson <accessToken 이 든 json>
project_support\tools\credentials.ps1 -OpenSkyFromJson <clientId/clientSecret 이 든 json>
```

기존 파일은 시간이 붙은 `.replaced-*` 사본으로 보존한 뒤 덮어쓴다. 변경 후에는 서버를 재시작해야 적용된다. 이 저장소는 사용자 프로필 안에 있으므로 프로필을 옮기거나 다른 계정 또는 장비에서 실행하면 다시 등록해야 한다. 키 원본은 저장소에 커밋하지 않으며, 어떤 도구도 값을 화면이나 로그에 출력하지 않는다.

### 현재 키 출처

- Cesium ion 토큰: `D:\DTAMFramework\VisualizationModule_Source\Unreal\Environments\DTAMVisualization\Config\DefaultGame.ini`의 `IonAccessToken`과 같은 값이다. 위 `-CesiumFromUnrealConfig`로 언제든 다시 가져올 수 있다.
- OpenSky: 발급 계정에서 다시 내려받는다.
- 브이월드: 브이월드 오픈API(vworld.kr)에서 발급한 인증키를 `{"apiKey": "..."}`로 저장한다. 2026-09-09에 사용자가 준 키를 등록했다.


### 로컬 DEM 선택

설정 → 지도 표시 → 지형 자료에서 `Cesium World Terrain`(기본) 또는
`로컬 DEM 우선 + 범위 밖 Cesium`을 선택한다. 선택은 재접속 후에도 유지된다.
지형 기복 표시를 꺼 둔 경우 선택만 바뀌고 평면 표시를 유지한다.
새 API가 추가된 버전은 main.py 서버를 재시작하고 브라우저를 강력 새로고침한다.

로컬 패키지는 `data/workspace/terrain/user_dem/manifest.json`과 격자 파일이다.
원본 TIFF는 보존한다. 서버에는 GDAL 없이 연결되며 패키지가 없거나 실패하면
기존 지형을 사용한다. 현재 패키지는 30m급 원자료이며 수직 CRS 미표기로 인해
EGM96을 가정하고 공식 geoid로 타원체 높이를 보정했다. 원자료보다 정밀해진다는
뜻은 아니며 도심 융기와 건물 자체의 높이 오차가 해결된다고 보장하지 않는다.
자료 처리와 API 상세는 ADR 0024를 참고한다.
