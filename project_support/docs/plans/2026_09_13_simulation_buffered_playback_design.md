# Simulation 선행 계산 및 일관된 재생 설계

날짜: 2026-09-13
상태: 사용자 검토용 초안. 실행 코드 및 운영 서버 변경 전.

## 목적

계산 소요 시간의 순간적인 변동을 화면 재생에서 분리한다. 기체 운동뿐 아니라 운항 단계, 승하차, 게이트와 FATO 점유, 대기 사유가 하나의 표시 시각을 사용해야 한다. 지속적인 계산 능력 부족을 버퍼로 해결했다고 주장하지 않는다.

## 확인한 기존 구조

- `user_application/uam_mission/scenario_session.py`는 현재 시계에 맞춰 엔진을 전진시키며 조회도 그 엔진을 읽는다. 현재 기록은 전체 운영 화면을 재현하는 기록 계약이 아니다.
- `user_application/uam_mission/scenario_observation.py`는 기체 및 시설 정보를 현재 엔진에서 계산한다. 지도만 지연시키면 정보창과 시각이 달라진다.
- `data/simulation/flight_runs.py`에는 단일 비행의 기록과 재생을 위한 저장 구조가 있다. 다중 비행의 모든 시설 상태까지 저장하는 구조는 아니다.
- 확인한 `communication/python/native_pilot.py` 공개 연결에는 제어기와 물리 상태 전체의 체크포인트 저장/복원 호출이 없다. 위치만 복원해서 운항을 이어 가는 방식은 사용하지 않는다.
- 최근 Physical 관측 재생 작업은 별개이며 변경하지 않는다.

## 선택지와 권고

1. 전체 계산 후 재생: 실행 중 계산 병목의 영향을 가장 적게 받지만 준비 시간이 길고 즉시 개입이 어렵다.
2. 선행 버퍼 재생: 짧은 준비 후 계산과 재생을 병행한다. 일시적인 지연은 흡수하지만 지속적인 과부하에서는 재버퍼링이 필요하다.
3. 현행 실시간 실행: 조건 변경이 즉시 반영되지만 계산 지연이 재생에 영향을 준다.

권고: 현행 모드를 보존하고 같은 기록 계약 위에 2번과 1번을 순차 추가한다. 조건 변경은 우선 현행 실시간 모드에서만 지원한다. 이 제한은 사용자 확인 대기 중이다.

## 시간과 상태 소유권

- 계산 완료 시각과 표시 시각을 명시적으로 분리한다. 화면 전체가 하나의 표시 커서를 사용한다.
- 계산 작업의 현재 상태는 기존 runtime/engine만 소유한다. 재생 자료는 이미 계산이 끝난 불변 기록이며 data가 소유한다. 조작 가능한 runtime 복사본을 만들지 않는다.
- 각 기록 묶음은 실행 ID, 순번, 계산 시각, 기체 상태, 운영 상태, 해당 시각까지의 사건을 연결한다. 정적 계획과 시설 정의는 실행 시작 시 버전과 해시로 고정한다.
- 지도와 정보 조회는 표시 묶음 ID를 사용한다. 계산 중인 엔진을 조회하는 우회 경로를 남기지 않는다. 요청 도중 표시 커서가 바뀌어도 응답의 시각을 구분하고 오래된 응답을 폐기한다.
- 불연속 상태(착륙, 게이트 변경, 승하차, 허가)는 다음 기록을 미리 노출하지 않는다. 위치 및 자세 보간만 별도 표시 처리로 허용한다.
- 예측 입력은 표시 시각까지의 이력으로 제한한다. 선행 계산된 실제 결과를 예측기에 공급하거나 예측 정확도 평가에 유출하지 않는다. 대응하지 못한 예측 기능은 이유와 함께 비활성화한다.

## 계산과 표본 주기

- native 물리 및 제어 주기와 실행 순서는 바꾸지 않는다. 외부 엔진 전진 구간의 분할도 결과에 영향을 줄 수 있으므로 기준 실행과 비교한다.
- 10 Hz는 우선 검토할 표시 전달 목표이지 native 계산을 10 Hz로 낮추라는 의미가 아니다. 원본 표본이 더 느린 경우 보간된 표시 표본을 원본 계산 결과로 표기하지 않는다.
- 작업자는 고정된 입력으로 순서대로 계산한다. 계산과 화면 전송을 분리하며 파일 쓰기나 브라우저 연결이 native 스텝을 건너뛰게 하지 않는다.
- 현재 계획을 전체 재계산하는 것은 별도의 명시적인 작업이다. 현재 운영 중인 엔진을 테스트용 작업으로 사용하지 않는다.

## 버퍼와 재생

- 초기 선행 목표는 시뮬레이션 시간 3초다. 10배 재생에서는 3초가 실제 시간 0.3초라는 점을 표시한다. 배속 지원 여부는 실측 처리량과 버퍼 상한에 따른다.
- 두 개의 유효한 위치 표본 등 재생에 필요한 자료가 확보되기 전에는 준비 상태를 유지한다. 표시 시각이 마지막 완전한 묶음을 넘지 않도록 제한한다.
- 자료가 부족하면 지도와 운영 시계를 함께 멈추고 '계산 대기'를 표시한다. 위치를 외삽하거나 시간을 건너뛰지 않는다. 목표 여유가 다시 확보되면 재개한다.
- 일시정지 중 작업자는 지정된 선행 상한에서 멈춘다. 전체 계산 모드만 작업 완료까지 계속한다.
- 전체 계산 완료와 화면 재생 완료를 구분한다. 계산 완료만으로 현재 화면에 모든 비행이 완료되었다고 표시하지 않는다.

## 자원과 수명 관리

- 한 작업의 계산 엔진은 단일 소유자가 생성하고 종료한다. 초기에는 선행 계산 작업 하나만 허용한다. 기존 실행과 동시에 CPU를 무제한 사용하지 않도록 작업 실행을 제한한다.
- 기록은 분할 파일과 인덱스로 순차 저장하고 필요한 구간만 메모리에 읽는다. 메모리와 디스크 상한은 운용 구성에서 정하며 실제 100대 자료 크기 측정 후 기본값을 확정한다.
- 상한 도달 및 쓰기 실패는 명시적인 정지/실패로 처리한다. 기존 기록을 자동 삭제하거나 불완전 파일을 완료 기록으로 공개하지 않는다.
- 취소, 재설정, 새 계획, 종료 시 기존 작업 ID를 무효화하고 늦게 도착한 결과를 버린다. native 핸들, 파일, 작업자 종료를 확인한 뒤 새 작업을 시작한다.
- 재생 되감기는 저장 자료의 조회다. 제어기를 되감았다는 의미가 아니다. 초기 버전에서는 저장되지 않은 구간의 탐색을 허용하지 않는다.
- 미래의 개입 재계산은 별도 범위다. native 제어기, 임무 상태, 교통관리, 예약, 난수 등의 일관된 복원 또는 시작점부터의 재실행이 먼저 검증되어야 한다.

## 화면과 호환성

- 기존 Simulation 템플릿 안에 실시간/버퍼 재생/전체 계산 후 재생 선택을 둔다.
- 준비 상태, 재생 시각, 계산 완료 시각, 확보된 버퍼 시간, 배속, 대기/실패 사유를 구분한다.
- 재생 중 지원하지 않는 운항 변경은 화면과 API 양쪽에서 거절하고 실시간 모드 안내를 제공한다. 조회, 추적, 시각화 켜기/끄기는 허용한다.
- 기존 단일 비행, Physical 입력, 기존 기록의 열람은 유지한다. 새 저장 및 공개 계약은 구현 전에 ADR과 버전을 추가한다.

## 검증과 적용 기준

1. 기존 실행과 같은 입력/전진 순서에서 상태 및 사건 결과 비교. 원본 표본과 표시 보간 결과를 별도 검증한다.
2. 지연, 빈 버퍼, 배속 변경, 일시정지, 취소, 계산 예외, 디스크 부족, 오래된 작업 결과를 자동 시험한다.
3. 같은 묶음에서 기체, 버티포트, 대기 사유, 승객과 사건의 시각 일치 및 미래 정보 차단을 시험한다.
4. 고정된 100대 입력으로 계산 처리량, 표본 크기, 메모리 상한, 준비 시간, 버퍼 부족 횟수와 표시 간격을 측정한다. 짧은 벤치마크를 하루 전체 성능으로 일반화하지 않는다.
5. 브라우저에서 추적 카메라, 정보창, 시설 점유, 배속, 끝까지 재생을 확인한다. 필요한 UAM 임무 회귀와 실제 Unreal 검증은 별도 실행 증거로 구분한다.
6. 운영 계획 및 기록을 보존한 별도 검증을 먼저 수행한다. 운영 서버 재시작은 실행 주체 확인과 기존 동의 범위 내에서만 수행하며 현재 권한 문제를 우회하지 않는다.

## 진행 단계

설계 확인 → 저장/조회 계약 및 ADR → 일관된 기록 생성 → 버퍼 재생 → 전체 계산 재생 → UI와 관측/예측 경계 검증 → 성능/운항 회귀 → 운영 반영.

이 문서는 설계 초안이며 구현 완료 또는 성능 개선 검증 결과가 아니다.
