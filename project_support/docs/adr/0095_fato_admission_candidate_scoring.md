# ADR 0095: 출발 전 FATO 후보에 진입 예약 대기 반영

## 배경

활성 비행의 도착 ETA와 패드 슬롯은 배정에 반영되지만, 아직 주기장에서 대기하는 기체의 `_entry_forecasts`는 배정 비용에 들어가지 않았다. 예약을 만든 뒤에는 항로를 고정하므로, 빈 패드가 남아도 같은 도착 패드의 줄이 길어질 수 있었다.

## 결정

기존 진입 간격 계산을 읽기 전용 `_preview_arrival_entry`로 분리한다. 실제 예약과 후보 비교는 같은 대기열 규칙을 쓰되, 후보를 비교하는 동안 예약이나 항로 고정을 하지 않는다. `fato_assignment.choose`의 선택적 `entry_wait` 콜백이 반환하는 대기를 출발 패드 대기 이후의 예상 도착 시각에 더한다. 기존 차단 기체 우선 회피와 도착 패드 슬롯 검사를 유지한다.

후보마다 별도 동역학 예측을 실행하지 않는다. ScenarioPilots의 `cached_entry_estimate`는 준비된 캐시만 읽고, 없으면 기존 보수적 구간시간 추정을 쓴다. 실제 진입 예약 단계는 기존처럼 native 예측을 요청한다. 따라서 캐시가 없는 후보의 비용은 근사치이며, 선택 후 대기가 추가될 수 있다.

내부 Python 호출만 변경한다. 외부 wire schema, 모델 패키지와 현재 상태 소유권은 바꾸지 않는다. 주기 중의 명시적인 departure_wait 지시만 화면에 표시한다. entry_s가 있는 경우 PSU, 없는 경우 운항 일정 대기로 구분하며 과거 공중 지시는 주기 중에 표시하지 않는다.

## 유지하는 제한

FATO 역할과 연결 항로, 유도로, 패드 점유 및 인접 패드 검사, 터미널 경로 충돌 검사, 패드별 분리 간격과 비행 중 항로 고정을 유지한다. 패드 개수를 늘려도 공용 경로가 있으면 실제 처리량이 증가한다고 보장하지 않는다. 다운워시나 실제 운항 인증 기준을 검증한 변경이 아니다.

## 검증

주기장 예약 누락 및 후보마다 native 추론을 시작하는 문제를 실패 시험으로 재현한 뒤 수정했다. 1개/4개 실제 레이아웃으로 동일한 12건의 진입 예약을 비교하고, 각 레이아웃에서 native 4편 완료와 자원 해제를 확인했다. 수치와 한계는 data/development_log/evidence/2026_09_15_fato_admission.json에 기록한다. 운영 서버를 재시작하지 않았다.
