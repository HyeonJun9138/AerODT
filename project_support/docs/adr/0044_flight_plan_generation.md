# ADR 0044 — 비행계획을 우리가 만든다: Mission Scheduling을 어디에 둘 것인가

- 날짜: 2026-09-11
- 상태: 채택
- 관련: [0038 하루치 비행계획](0038_scheduled_day_rehearsal.md),
  [0039 수요 분배 가중치](0039_demand_distribution_weights.md),
  [0042 운항 속도](0042_uam_operating_speeds.md)

## 배경

다중 비행 설정은 다섯 단계를 다 받아 놓고도 마지막 한 걸음이 없었다. **생성 요청**을 누르면
`/api/simulation/plans/multi`로 요청이 나가고 404가 돌아왔다. 하루치 비행계획은 바깥에서
받은 `FPL_all.csv`를 읽어 재생하는 것만 됐다(0038). 즉 **계획을 읽는 쪽은 있는데 쓰는 쪽이
없었다.**

같은 자료로 계획을 만드는 코드가 협력사 쪽에 있다(`Vert Scheduler`, FastAPI + 로컬 웹앱).
우리 `network` export를 그대로 받아 수요를 만들고 기체를 배정해 FPL을 뽑는다. 그러나 그것을
통째로 들여오는 것은 두 번째 앱을 우리 저장소 안에 두는 일이고, 그쪽은 자기 항로 탐색·지상
자원 모델·6DOF에 못 미치는 자체 비행 모델을 함께 들고 온다. **우리에게는 그 세 가지가 이미
있다.**

## 결정

### 1. 아키텍처상의 자리: Digital Layer의 Mission Scheduling

계획 생성기는 **Digital Layer**에, Simulation Engine Module 옆에 둔다. AI 계층이 아니다.

근거는 입력과 출력이 정한다. 이것이 먹는 것은 Shared Digital Model Library가 들고 있는
것(버티포트 형상, 항로망, 기체 성능)과 수요 시나리오이고, 내놓는 것은 Simulation Engine
Module의 입력 그 자체(**Scenario / Parameters**)다. 즉 계획 생성은 트윈이 재생할 시나리오를
만드는 일이며, 그 자리는 엔진 바로 앞이다.

```
Shared Digital Model Library ─┐
                              ├─▶ Mission Scheduling ─▶ [비행계획 계약] ─▶ Simulation Engine
수요 시나리오 (User Layer) ───┘                              ▲
                                                             ┆ (같은 계약)
                          PRISM · Planning Outputs ┄┄┄┄┄┄┄┄┄┘
```

**이 그림의 요점은 화살표가 아니라 가운데의 계약이다.** 비행계획은 이미 형식이 하나 있다 —
`flight_schedule.py`가 읽는 33열 CSV. 결정론적 생성기와 PRISM의 계획 출력을 **같은 계약의 두
생산자**로 두면, 나중에 AI 계획기를 붙일 때 엔진도 화면도 바뀌지 않는다. AI를 나중에 끼워
넣을 수 있게 만드는 값은 여기서 나온다. 그래서 생성기는 PRISM 안이 아니라 PRISM **앞**에
있고, PRISM은 이 계약을 대체하거나 다듬는 쪽으로 붙는다.

수요 생성(공간 비율 × 시간대 곡선 × 시드)은 계획이 아니라 **모델**이므로 Environment Model
옆의 Demand Model로 둔다.

### 2. 우리 저장소에서의 자리

| 조각 | 위치 | 왜 |
|---|---|---|
| 시간대 곡선, OD 배분 | `digital_twin/model_library/demand_profile.py` | 순수 규칙. 파일도 시계도 없다 |
| 그리디 이벤트 배정, FPL 쓰기 | `digital_twin/model_library/flight_scheduler.py` | 읽는 쪽(`flight_schedule.py`)과 같은 층, 같은 열 정의를 import |
| 조립·수명·진행률 | `user_application/uam_mission/plan_generation.py` | `scenario_session.py` 바로 옆. 만들고 곧바로 넘긴다 |
| 배선 | `communication/web/plan_generation_routes.py` | 시작 / 진행 / 파일 |
| 화면 | `user_application/web/scheduling_progress.js` | 채워지는 글자 하나 |

### 3. 협력사 코드에서 가져온 것과 가져오지 않은 것

**가져온 것(기능):** 시간대별 통행 곡선 24개 값, 시간대 단위 수요 배정 정책, 기체 가용
시각 힙으로 도는 그리디 배정, 정원을 채울 수 있는 목적지를 인원 비례로 뽑는 규칙,
도착 자원을 못 잡은 편을 미해결로 들고 가는 방식.

**가져오지 않은 것:** 그쪽의 항로 탐색, 지상 자원 시뮬레이터(`vp_sim`), 0.1초 적분 비행
모델(`aircraft_runtime`), 고도·경사 검증. 우리는 그 자리에 **`flight_plan.build_plan`을
쓴다.** 이것이 이 ADR에서 가장 중요한 선택이다: **배정에 쓴 시간이 나중에 실제로 나는
계획의 시간과 같다.** 엔진(`scenario_engine.py`)이 같은 항로를 같은 방법으로 다시 만들기
때문에, 파일에 적힌 시각은 다른 무언가의 추정이 아니다.

고도를 고르지 않는 것도 같은 이유다. 어디를 어느 높이로 가는지는 항로망의 답이고 조종사가
난다. 스케줄러는 **누가 언제 어디서 어디로**만 정한다.

### 4. 해결하지 않고 남기는 것

계획은 **의도**다. 최적화하지 않는다 — 탐색도 개선도 없고, 이 하루가 가능한 최선이라고
주장하지 않는다. 도착 주기장을 못 잡은 편은 `arrival_unresolved`로 그대로 들고 간다.
0038이 정한 대로 **하루를 미리 풀지 않기** 때문이다: 어느 편이 적힌 대로 날 수 없는지가
리허설이 답하는 질문 전부이고, 여기서 풀어 버리면 아무도 보기 전에 끝나 버린다.

시간대가 끝나면 남은 수요는 이월하지 않고 미처리로 센다. 기체가 모자란 것이 **다음 시간이
밀리는 모습**이 아니라 **미처리 승객 수**로 보이게 하려는 것이다.

## 결과

실제 저장 망(버티포트 18, 지점 135, 링크 220, 153쌍)으로 67,500명·06:30–21:30·기체 90대를
요청하면 **1,644편이 31초에** 나오고, 그대로 트윈에 적용되어 재생 가능한 하루가 된다.
`flight_schedule.read_schedule`이 0개 문제로 되읽는다.

그 실행이 드러낸 것 두 가지를 숨기지 않고 기록한다.

- **306개 정렬쌍 중 항로망이 잇는 것은 14개뿐**이고 292개는 합성 직항 회랑으로 난다.
  `air_graph`가 링크를 단방향으로 보기 때문이며, 협력사 쪽도 같은 자료에서 F 152개에
  역방향을 허용해야 306개가 이어진다고 적어 두었다. 우리 자료에 역방향 링크를 넣거나
  `air_graph`가 F를 양방향으로 읽게 하는 것은 별도 결정이다.
- **1,644편 중 59편이 도착 주기장을 못 잡았다.** 모든 게이트에 기체를 채우고 시작했기
  때문이며, 특정 데크(VP016, VP009)에 몰린다. 이것은 결함이 아니라 그 하루의 사실이다.
