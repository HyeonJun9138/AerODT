# 수동 도착의 접근 허가와 착륙 허가 분리

## 원인
계속 갱신되는 예상 접지 시각 `cleared_s`를 수동 착륙 요청의 대기 종료 시각으로 사용했다. 정지 대기하는 수동 기체는 예상 접지가 계속 뒤로 밀려 요청할 수 없었다. 자동 운항은 별도 접근 시작 판정을 사용했다.

## 결정
기존 manual request endpoint에 `approach` 종류를 추가한다. procedure.version을 2로 올린다. 다른 wire 필드는 유지한다. 접근 순번 배정은 접근 허가가 아니다. 수동 접근 요청은 기존 PSU begin_approach의 선행 순번, 접근 간격 및 용량 판정을 통과해야 한다. 허가는 기체를 움직이지 않는다.

수동 최종 착륙 요청은 접근 허가와 실제 관측 기반 final_guard 구간 진입이 선행되어야 한다. 예상 접지 시각 도달 조건을 제거하고 실제 패드, 예약 및 이착륙 간격, 선행 접근, 터미널 경로, 현재 GATE 및 지상 출구를 확인한다. 수동 선착륙/점유 GATE 대기는 이번 변경에 추가하지 않는다.

화면 eligibility와 POST는 같은 자원 검사 함수를 사용한다. 이전 요청 거절 문구가 새 판정을 덮어쓰지 않는다. v2 화면/알림은 procedure를 지시의 기준으로 사용하며 EAT나 접지 예상으로 접근 시작을 지시하지 않는다. HOLD는 허가 취소 요청임을 버튼에 명시한다. 새 충돌/위치 지연이 확인되면 최종 착륙 허가를 재확인하도록 한다.

## 호환성과 배포
기존 landing 요청으로 접근 단계를 건너뛸 수 없다. 기존 브라우저에도 next.kind/label 동적 처리 경로가 있지만, 절차 단계/알림의 정확한 표시를 위해 프런트엔드를 같이 갱신해야 한다. 활성 시뮬레이션 서버는 소스 수정만으로 재로딩하지 않는다. 실행 중 비행을 중단하거나 허가를 임의 발급하지 않는다.

## 검증 범위
moving ETA 반복 갱신, 선행 간격, 자원 점유, 위치 지연, 명시적 접근, 실제 위치 기반 최종 요청, 허가 취소, 멱등 요청, UI 표시와 dispatch 회귀시험. 실제 비행 운영 및 전기체 검증은 별도이다.
