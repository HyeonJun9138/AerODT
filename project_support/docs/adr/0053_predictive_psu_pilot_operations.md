# ADR 0053: 예측 접근 허가와 조종사 교통 대응

Date: 2026-09-11
Status: Accepted

## 문제

다중 비행의 native 경로는 앞 기체가 접근 중인 동안 다음 기체도 같은 패드를 점유하려 해 접근 전체가 직렬화됐다. 계획 경과시간으로 만든 ETA는 실제 대기와 이동을 충분히 반영하지 못했다. 조종사 화면에는 운항 속도 설정만 있었다.

## 결정

- PSU는 실제 위치와 남은 경로, 단계별 속도로 ETA를 갱신한다. 발급한 착륙 번호를 유지하며 출발 예약, 주기장 확보, 선행 접근 ETA로 도착 슬롯을 다시 배치한다.
- 접근 개시와 최종 착륙 허가를 분리한다. 기본 접근 시작 간격은 30초, 패드별 동시 접근 한도는 3대다. 최종 구간에서는 선행 접근과 실제 패드 소유를 확인한다. 접지 후 지상 이동이 패드 중심에서 25m를 벗어나야 패드를 해제한다. 기존 조기 해제 설정을 끄면 주기장 도착까지 유지한다.
- 이미 접근하는 도착편이 출발 지상 이동·이륙 완료 전에 같은 패드를 요구하면 출발편은 주기장에서 기다린다. 빈 주기장이 나중에 확보되면 실제 도착 지상 경로도 그 주기장으로 바꾼다.
- 조종사는 기본 35초의 관측 속도 기반 최근접 예측을 사용한다. 순항 중 회랑 여유 안에서 우측 회피를 검토하고, 다른 주변 기체와의 예상 근접을 악화시키지 않는지 확인한다. 불가능하면 검증된 속도 조정 또는 경보를 유지한다. 접근 전방 교통에는 후행 기체가 감속 대기하며 교통 해소 후 8초 동안 상태를 확인한다.
- native RoutePilot에 목표 우측 편차와 속도 계수를 전달한다. C ABI는 4이며 `aerodt_pilot_traffic(handle, right_m, speed_factor)`가 추가된다. 위치·고도·충돌 판정의 소유권은 물리 runtime에 남는다. 이전 DLL로 비중립 교통 지시를 보내면 명시적으로 실패한다.
- `GET /api/simulation/scenario/pilots`는 기체별 실제 상태, clearance, instruction, 적용 정책을 반환한다. 지시에는 접근·최종·대기 구분과 교통 대상, CPA, 우측 편차, 속도 계수가 포함된다. `Cache-Control: no-store`이며 세션 잠금 아래 읽는다. 미로딩 상태는 빈 기체 목록이다.
- PSU/조종사 Decision Chart와 live GUI가 같은 정책과 지시를 사용한다. 조종사 GUI는 기체 선택, 운항 카드, PSU 지시, 교통 대응, 단계별 계획 속도 설정으로 구성한다. 차트는 가독성 유지를 위해 원래 크기로 스크롤한다.

## 검증

- 독립 Release native build / CTest 18/18. 우측 편차를 적용한 실제 native 비행의 복귀·고도 유지·착륙 및 잘못된 명령 거부 검증.
- 최종 관련 Python 44/44, 관련 Node 47/47, architecture PASS.
- 전체 web_live 회귀 시 929 통과, 기존 시각 의존 위성 한국 범위 fixture 4건 실패. 해당 위성 코드는 변경하지 않았다.
- 동일 6대 시나리오에서 예측 접근 끔/켬 비교: 누적 체공 2,854→132초, 전체 완료 2,148→1,342초, 두 조건 모두 6편 완료·native 실패 0. 새 방식은 최대 3대 동시 접근, 동일 패드 동시 수직 착륙 표본 0.
- 실제 저장 100대 편성의 30분 native 실행 및 브라우저에서 실제 패널과 API를 확인했다. 상세 수치와 실행 버전은 development_log evidence에 기록한다.

## 한계

ETA는 고정밀 비행 궤적 최적화가 아닌 실제 잔여 경로 기반 추정이다. 교통 대응은 짧은 시간의 관측 속도 기반 예측이며 지형, 장애물, 인증된 항공 분리나 전체 충돌 안전성을 보장하지 않는다. 대기 시 native 감속·위치 유지 기법을 사용하며 자동 회항 경로는 새로 만들지 않는다. 실제 Unreal과 원격 GPU 비행 영상은 이번 검증 범위에 포함하지 않았다. 6대 비교의 개선율을 모든 편성에 일반화하지 않는다.
